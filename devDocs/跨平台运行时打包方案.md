# 跨平台运行时打包方案（2.02.88）

> 建立于 2026-10-11。**目标**：落实 2.02.88「**JRE 改用 GraalVM**」在**各目标平台**的运行时选型与校验口径。
> 相关：工作卡 `DevAgentControl/CURRENT_STATE_JDK升级选型.md`；选型/迁移计划 `src/com/DocSystem/websocket/office/docs/GraalJS替代Nashorn评估计划.md`（§6.1/§6.2）。
> **本版（2.02.88）允许放弃对部分平台的支持**（用户 2026-10-11 裁定）。

## 1. 背景

产品默认 JS 引擎已翻转为 **`graaljs`**（阶段 1，2026-10-07），因此**运行时必须能提供 GraalJS**：要么运行在 **GraalVM**（自带 GraalJS），要么 classpath 上有 GraalJS 的 jar。
2.02.88 把随产品的 `tomcat\java\jre` 换成 **GraalVM CE for Java 8**。
难点：**GraalVM CE 的 java8 发行版平台覆盖很窄**，导致部分平台没有可用的 GraalVM java8。

## 2. 事实：GraalVM CE for Java 8 的平台覆盖（已核实）

| 平台 | java8 发行版 | 备注 |
|---|---|---|
| Linux x86_64 (amd64) | ✅ | 一直有；**最后一个 java8 版 = 21.3.1** |
| Windows x86_64 (amd64) | ✅ | 同上 |
| **macOS x86_64** | ⚠️ **仅到 21.0.0.2** | 自 2021-04 CPU 起不再提供；**21.2.0 已无 darwin 包** |
| Linux aarch64 / macOS aarch64 | ❌ **从未有过** | java8 无 aarch64；首个 darwin-aarch64 是 22.1.0（仅 JDK 11/17）|
| Windows aarch64 | ❌ | 从未有过 |
| 鸿蒙 HarmonyOS | ❌ | 无 JVM（运行时是 ArkCompiler/ArkTS），传统 Tomcat 无受支持路径 |

## 4. 运行时如何被产品消费

- 落点：替换 `tomcat\java\jre`（4 个启动脚本 `docsys_start.bat` / `docsys_restart.bat` / `docsys_start_hidden.bat` 等把 `JAVA_HOME`/`JRE_HOME` 指向它）。

## 5. 风险与注意

1. **全平台统一 GraalJS 21.2.0**：Win/Linux/麒麟 x64 由 GraalVM 21.2.0 运行时内置提供；Mac / ARM64 由随包 `WebRoot/WEB-INF/lib` 的 21.2.0 jar 提供 → **JS 行为一致**（已实测）。差异只在 JVM（GraalVM vs stock）→ **仅性能差异**（stock 上解释执行 ~3.2 s vs GraalVM ~1.3 s）。
2. **不采用** GraalVM java8 **21.0.0.2** —— 其 GraalJS 21.0.0 在 xlsx(cell) 上与 21.2.0 行为不一致（实测 cell 内容不同=5）。
3. **原生库审计（ARM/Mac 的关键 —— 实测 `WEB-INF/lib` + 全仓库代码扫描，2026-10-11）**：
   - `lwjgl` / `lwjgl-freetype`：**有 `arm64` 与 `macos-arm64`** ✅ → **Office 字体渲染（编辑/转换核心）在 Apple Silicon / ARM64 可用**。
   - **`opencv` / `tesseract` / `leptonica` / `openblas`：全仓库代码零引用 → 未被使用**。其缺 macos/arm64 native **对功能无影响**（且属 ~100MB+ 死重量，可考虑清理）。
   - `ffmpeg`（javacv，仅用于**视频预览转码** `CovertVideoUtil.convertVideoToMp4`）：有 `linux-arm64`、**无 macos**；且该方法 **catch 全部异常→返回 false**（调用方用原文件兜底，优雅降级）→ **Mac 上"视频预览转码"不可用但不报错**；Linux ARM64 可用。
   - `sevenzipjbinding`（**压缩包解压/查看**，`BaseController`）：natives 仅 `Linux-amd64/i386`、**`Mac-x86_64`**、`Windows-amd64/x86` → **无 arm64** → **"压缩包内文件查看"在 Apple Silicon（aarch64 JVM）与 Linux ARM64 不可用**；**Mac Intel ✅**。
   - `org.bytedeco.librealsense`（`src/util/LuceneUtil/LuceneUtil2.java:79`）：**废 import（未使用）**，无影响。
   ⇒ **结论**：**核心 Office 编辑/转换在 ARM/Mac 可行**；受影响的只有两个**非核心**功能 —— **"压缩包内查看"（Apple Silicon / Linux ARM64）** 与 **"视频预览转码"（Mac）**。若要补齐：升级 `sevenzipjbinding` 到带 arm64 的版本 / 为 Mac 提供 ffmpeg natives / 或让这些功能在这些平台降级。
4. **麒麟 x64**：glibc 版本足够即可（同一 Linux x64 二进制）；实机冒烟。
5. **各 stock-JDK 平台（Mac Intel / Mac Apple Silicon / 麒麟·Linux ARM64）均需实机冒烟**（引擎语义已在本机复验，但各平台 JDK/启动器/原生库需实机确认）。

1. **GraalJS 21.0.0 与 21.2.0 在 xlsx 上行为不同**（21.0.0 多出 style/string 条目）；**21.2.0 才是与旧 nashorn 基线一致的那一侧**。故 **Mac 若用 GraalVM 21.0.0.2，xlsx 产物会与其它平台不一致**（风险）。

3. 因此 Mac 有两种候选：**(A) GraalVM 21.0.0.2**（快、但 xlsx 行为不一致）；**(B) stock JDK8 + 21.2.0 jar**（行为一致、略慢）。
4. 附加红利：路线 B **不依赖 GraalVM 的平台覆盖** → 理论上可把 **Apple Silicon / ARM64 也支持回来**（原生 JDK8 即可）。

## 11. 安装包结构裁定（2026-10-11）：方案 B「通用 payload + 按 OS 外壳」

### 11.1 起因

现状是**每个 OS 一套完整包**（各含 MySQL + JRE）。用户提出权衡：若把 MySQL 从 `docs` 里拿掉，是否就能"同一个 docs + 换 JRE"出各平台包？代价是客户要自己装 MySQL。

### 11.2 现状实测（2026-10-11，`C:\TomcatForDocSysDev\docsys`）

| 组成 | 体积 | 是否 OS 相关 |
|---|---|---|
| `tomcat/` | 1064 MB | **是**（内含 `java/jre` 472 MB） |
| `mysql/` | **216 MB（17%）** | **是**（原生二进制 + symlink） |
| 顶层启动脚本 / `data` / `agent` / `skills` / `logs` / `tmp` | ≈0 | **是**（顶层 11 个文件**全是 `.bat`** + `sleep.vbs`，无 `.sh`） |
| **合计** | **1280 MB** | — |

**关键事实（均已核实）**：

1. **出厂默认库就是 SQLite**：`src/jdbc.properties` = `db.type=sqlite` / `db.driver=org.sqlite.JDBC` / `db.url=jdbc:sqlite:${catalina.home}/DocSystem.db`（`WebRoot/WEB-INF/classes/jdbc.properties` 同）。
2. **MySQL 不参与默认运行路径**：`start.bat` 只起 `monitor_start.bat` + `docsys_start.bat`，**不启 MySQL**；要 MySQL 才另跑 `mysql_start.bat`（`mysql\bin\mysqld --defaults-file=mysql\bin\my.ini --standalone --console`，用 `template-my.ini`/`template-ctl.bat` 现场生成配置）。
3. **切库是纯配置**：`docsys_start.bat` 启动时若存在 `tomcat\webapps\docSys.ini\jdbc.properties`，就**覆盖**到 `WEB-INF\classes\jdbc.properties`；`ManageController` 里也有 `jdbcConfig` 写入逻辑（页面本身可配库）。
4. **JDBC driver 是纯 Java、已随 WAR**：`mysql-connector-java-8.0.15.jar`（2.04 MB）、`sqlite-jdbc-3.41.2.2.jar`（12.26 MB，各平台原生库封装在 jar 内）→ **数据库选择与打包无关**。
5. **`mysql` 与 `jre` 是两个"原生件"** → 当前按 OS 分别打包，本质是被 `{JRE × MySQL}` 的组合数逼出来的；`docs` 里其余 ~600 MB payload（WAR + office 编辑器 + tomcat 的 jar/配置）**本来就全平台通用**。
6. **symlink 只是次要病根**：Windows 解压异常源于归档里存了符号链接（打包时**解引用**即可修：`zip` 不加 `-y`、GNU `tar` 加 `-h`），但**不能**解决根本问题 —— `mysqld` 二进制按 OS 不同（`mysqld.exe` vs ELF），**只要随包 MySQL 就必然 per-OS**。
7. **"一份 docs 通吃"还差顶层脚本**：现在顶层启动脚本是纯 `.bat`，Linux/Mac 跑不了。

### 11.3 裁定（用户 2026-10-11）：**方案 B**

> **方案 B**：`docs` 做成**平台无关 payload**（不含 JRE、不含 MySQL）+ **按 OS 的外壳（JRE + 平台启动脚本）**；**默认走 SQLite 开箱即用**（通用 payload 真正零外部依赖）；**MySQL 降为可选下载件**，而不是塞进所有人的基础包。
> 动机（用户原话）：「后续还想支持其他类型的数据库」—— driver 是纯 Java，加数据库 = 多一个 jar + 一个 `db.type` 值，**不必重打平台包**（若想更干净，可加外挂 `lib-ext` 目录，连 WAR 都不用重打）。

**结构**：

```
构建期（一次）   docsys-payload/                 ← 全平台通用（~600 MB）
                 ├── tomcat/{bin,conf,lib,webapps}     # 不含 java/
                 └── 启动脚本模板

打包期（每平台） docsys-<os>/                    = payload + jre-<os> + shell-<os>
                 ├── tomcat/java/jre/            ← GraalVM 21.2.0（Win/Linux x64/麒麟 x64）
                 │                                  stock JDK8 + 21.2.0 jar（Mac Intel/ARM、Linux ARM64）
                 └── start / docsys_start / docsys_stop / (mysql_start)   ← Win: `.bat`   Linux/Mac: `.sh`
```

**注意语义**：交付**仍是每平台一个包**，简化的是**准备过程**（维护面从 `{JRE × MySQL}` 两套原生件降为 `{JRE}` 一套，MySQL 只剩可选件），不是"一个文件通吃所有平台"。

### 11.4 由此产生的待办（方案 B 的代价，非可选）

| # | 项 | 说明 |
|---|---|---|
| B-1 | **新增 Linux/Mac 顶层 `.sh` 脚本** | `start.sh` / `docsys_start.sh` / `docsys_stop.sh` / 可选 `mysql_start.sh`；现顶层 11 个脚本全为 `.bat` + `sleep.vbs` |
| B-2 | **Linux/Mac 包改用 `.tar.gz`** | zip 会丢 `.sh` 可执行位、CRLF 也可能出问题；或在安装器里解压后 `chmod +x` |

### 12.3 三个"Linux 专属"阻塞点的实测结论

| 阻塞点 | Windows 侧能否解决 | 实测结论 |
|---|---|---|
| **`.sh` 可执行位** | ✅ 能 | **Git for Windows 的判定规则 = 文件以 `#!` 开头即为可执行**（实测：`a.sh`(有 shebang)→`755`、`b.sh`(无 shebang)→`644`、`c.txt`(有 shebang)→`755`）；**Git 自带 GNU tar 1.35**（`C:\Program Files\Git\usr\bin\tar.exe`）**如实写入 `-rwxr-xr-x`**。本仓库 14 个 `.sh` **全部有 shebang** → 直接可用。⚠️ **Windows 内置 `C:\Windows\system32\tar.exe`（bsdtar 3.8.8）不可用**：同一文件它写成 `-rw-rw-rw-`，且无 `--mode` 选项。7-Zip 19.00 同理（只认 Windows 属性）。 |

| **CRLF** | ✅ 无需处理 | `core.autocrlf=false`、无 `.gitattributes`；14 个 `.sh` 实测 **CRLF=0（全 LF）**。 |
| 归档内 uid/gid/uname | ✅ 无害 | 解压后归用户自己所有；可用 `--owner=0 --group=0 --numeric-owner` 规整。 |

### 12.4 推荐做法（纯 Windows、可脚本化）


### 13.5 新发现：现有 Linux/mac 发布包的非 ASCII 文件名是乱码

参考包（Linux 构建）里这 3 个文件名是**转码坏掉**的（CP437 字符，实为 GBK 字节被当 UTF-8/CP437 处理）：

| 应有名称（仓库 / dev / payload / git 四处均为 UTF-8 正确名） | 参考包里的乱码 |
|---|---|
| `web/images/AI智能体.png` | `AI\u2553\u255f\u2500\u2584\u2560\u0445.png` |
| `web/images/AI接入.jpeg` | `AI\u255c\u2559\u255a\u044b.jpeg` |
| `web/static/sdkjs/word/Documents/Изменение настроек таблиц по умолчанию.docx` | `\u0437\u043a\u0437\u2518…` |

- 依据：`WebRoot/web/images/`、dev 部署树、payload 三处名字都是 `AI智能体.png`；`git ls-files` 记录的也是 UTF-8（`\346\231\272\350\203\275\344\275\223`）。
- ⇒ **Windows 侧打包反而修正了这一点**；但也提示：**他们现有 Linux 打包链路会破坏所有非 ASCII 文件名**（当前只有这 3 个受影响；`AI智能体.png` 是 UI 引用的图片，在 Linux/mac 上可能 404）。

**根因定位（2026-10-12）**：`Linux/PrepareLinuxPackage.sh` 里有这一步 ——

```bash
cd ${CURRENT_DIR}/docsys/tomcat/webapps/DocSystem/
unzip DocSystem.war          # ← 在非 UTF-8 locale 的 Linux 下解压，会把非 ASCII 名转码坏
```

这是典型的 `unzip` 编码问题（`unzip` 默认按本地 CP437/GBK 解释 zip 里的名字）。**修法**：改用 `unzip -O UTF-8`、或先 `export LANG=zh_CN.UTF-8`、或用 `jar xf` / `python3 -m zipfile -e`；**而走 Windows 侧打包则完全不经过这一步**（Windows 上解压 WAR 得到的是正确 UTF-8 名），所以新包天然正确。

### 13.8 打包器缺陷 3：`--list` 在中文 Windows 控制台崩溃（2026-10-12 已修）

**现象**（默认控制台 `chcp` = 936 / GBK）：

```
> python C:\docsysRel\build_release.py --list
UnicodeEncodeError: 'gbk' codec can't encode character '\u2717' in position 50: illegal multibyte sequence
  File "C:\docsysRel\build_release.py", line 888, in main
    log("  payload   : %s（%s）" % (args.payload, payload_state(args.payload)))
```

**根因**：脚本用 `✓ / ✗ / ⚠️ / ▶` 作状态标记，这些码位**不在 cp936 编码表内**；中文 Windows 上 `sys.stdout.encoding` = `gbk`，`print()` 遇到编不出的字符即抛 `UnicodeEncodeError`。**这个崩溃一直是潜伏的** —— 只有"payload 未就绪"（要打印 `✗`）或"运行时缺失"时才显形；此前几次打包都输入齐全，所以没碰到。换言之：**它恰好会在"按 §15.2 流程第一次跑"时出现**，是流程的必经路径。

**修法**（在 `log()` 出口统一做编码降级，中文照常输出）：

- `_safe_text()`：先整体 `text.encode(sys.stdout.encoding)` 试一次 —— 能编就**原样返回**（零开销、零改变，Linux/UTF-8 控制台行为完全不变）；
- 只有整体编不出来时才**逐字符** `encode`，把编不出的字符按 `_ASCII_FALLBACK` 表降级：`✓→OK`、`✗→!!`、`⚠→!`、`▶→>`、变体选择符 `U+FE0F→""`；表里没有的兜底 `?`；
- `log()` 改为 `print(_safe_text(msg), flush=True)`。

**为什么不用 `sys.stdout.reconfigure(encoding="utf-8")`**：那样中文 Windows 下整个脚本的中文输出都会变乱码（控制台仍按 cp936 解码）。现在这套只牺牲 4 个符号，中文、路径、体积数字全部可读。
