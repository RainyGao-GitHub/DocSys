# 首启历史数据恢复方案（v2）

> v2 修订（2026-11-21）：
> 1. 恢复导入一律使用 `docsystem_data.json`（跨数据库类型安全），SQL 备份不用于恢复；
> 2. 恢复流程不直接修改 `WEB-INF/classes/docSysConfig.properties`——只写 `docSys.ini` 用户配置副本，由 `docSysInit(true)` 在"启动初始化"过程中统一应用（无需重启 Tomcat）；
> 3. 入口改为 index 页面级 radio 选择（全新启动 / 从已有数据恢复），首管弹窗（addFirstAdminUser）本次零改动。

## 1. 背景与目标

系统首启（数据库为空或不存在）时，目前直接弹出「添加系统管理员」弹窗走全新安装流程。但实际场景中很多用户并非全新安装，而是 **MxsDoc 安装目录损坏后重装**——此时磁盘上仍留有旧的数据根目录（`MxsDocData/DocSysReposes/DBBackup/<yyyyMMddHHmmss>/` 里每天自动备份的 `docsystem_data.json`），理应引导用户从备份数据恢复，而不是从零开始。

目标：

- 首启检测到「数据库为空/不存在」且「本机存在含有效备份的 DocSysReposes 目录（可能多个）」时，在 index 页面显示启动方式选择：**全新启动** 或 **从已有数据恢复**。
- 选全新启动 → 弹出现有的首管创建弹窗（现状流程，不动）；选恢复 → 用用户选定的备份恢复，成功后直接进入登录，失败可重新选择（换备份 / 改走全新启动）。
- 真正的全新安装（无任何历史数据）**行为完全不变**（零回归）。
- 支持跨数据库类型恢复（如旧系统 mysql 的备份恢复到全新安装的 sqlite）。

## 2. 现状梳理（可复用能力与关键事实）

| 能力 | 位置 | 说明 |
|---|---|---|
| 首管弹窗触发 | `UserController.getLoginUser` 返回 `needAddFirstAdmin` → `index.js` | 入口分支保持，仅在前面插入恢复检测 |
| 数据根目录扫描 | `DataRootService.getCandidates()` | 已扫描多个 DocSysReposes（Win 全盘 / Linux /data /opt /srv / user.home 等，2.5s 预算），候选已带 `hasValidBackup / lastBackupTime / backupCount` |
| 备份信息读取 | `DataRootService.readBackupInfo()` | 遍历 `DBBackup/<ts>/`；**目前只保留最新一条，需扩展为完整列表；恢复资格改为 json 有效** |
| 数据根目录应用 | `ManageController.applyDataRoot()` | 唯一调用方是 `addFirstAdminUser`（弹窗提交时会话中直接改 WEB-INF/classes 配置并立即生效）——属既有实现，本次不动、恢复流程也不复用此写法 |
| 启动配置机制 | `docSysInit()` 入口（BaseController:14926-14947） | 负责把 `docSys.ini/docSysConfig.properties`（用户配置副本）拷贝进 `WEB-INF/classes` 并重新初始化全局（路径/Redis/LDAP/LLM）；`docSysInit(true)` 可在会话中安全触发完整初始化 |
| 库表重建 | `deleteDBTabsEx()` / `initDBTables()`（BaseController） | drop 全部表 / 按当前版本建表；`initDBTables` 是 private，需提权或加包装 |
| JSON 导入 | `importDatabaseFromJsonFile()`（protected static） | `buildObjectFromJsonObj → dbInsert` 通用 JDBC 插入，含附加表（system_setting/Agent），**与数据库类型无关** |
| 建库 | `createDB()`（protected static） | sqlite 建文件 / mysql 建库 |
| 定时备份 | `addDelayTaskForDBBackup()` | 每天写一次 DBBackup（json 版在导出成功后拷贝），「最新备份」最多滞后一天 |

关键事实（决定恢复步骤的设计）：

1. **JSON 备份是对象级序列化**（`dbQuery → JSON.toJSONString`），导入是通用 JDBC 插入——天然跨数据库类型（mysql 备份可恢复到 sqlite，反之亦然）；SQL 备份是方言性 INSERT，跨库类型不可靠。**恢复一律用 JSON**。
2. 旧版本备份数据灌入当前版本表结构，与 `DBUpgrade` 语义完全一致（reset 新表 + 导旧数据，缺列走默认值）——**恢复完成后天然是当前版本 schema，无需版本迁移**。
3. sqlite 的 DB 路径来自 `jdbc.properties`（`${catalina.home}/DocSystem.db`），与 dataRoot 无关；恢复只涉及 `docSysConfig.properties` 的数据根目录配置，且该配置通过 `docSys.ini` + `docSysInit(true)` 在初始化过程中应用，无需重启 Tomcat。
4. DBBackup 挂在数据根目录的 DocSysReposes 下，「备份属于哪个数据根目录」是确定的，恢复时 dataRoot 固定为备份所在根（不允许自由输入）。
5. 定时备份 `skipDocTab=true`（DOCSYS_DOC 大表不备份），恢复后全文索引按需重建——与版本升级的既有行为一致。

## 4. 后端设计

### 4.1 DataRootService 扩展

1. `BackupInfo` 增加 `List<BackupEntry> entries`：`{dir, time, timeText, hasJson, jsonSize}`，按时间倒序；`readBackupInfo()` 顺手收集（现在本来就遍历所有目录，成本不变）。
2. **恢复资格判定**：备份目录必须存在非空 `docsystem_data.json`（SQL-only 的旧备份不进入恢复列表，时间太老的只有 SQL 的备份放弃恢复）。
3. 新增 `getRestoreCandidates(int osType, JSONObject currentPaths)`：复用 `getCandidates()` 的扫描与排序，过滤有 json 备份的候选根，返回每个根的完整备份列表；roots 按 `lastBackupTime` 降序。

### 4.2 新增接口（ManageController）

**`/Manage/getRestoreCandidates.do`**（POST，无参）

- 门禁：复用 `dataRootAccessCheck()`（系统未初始化时开放；初始化后仅超管）。
- 返回：

```json
{ "status": "ok", "data": { "roots": [
  { "root": "D:/MxsDocData/", "backupCount": 5, "backups": [
    { "dir": "20261120030000", "timeText": "2026-11-20 03:00:00", "jsonSize": 1234567, "latest": true },
    { "dir": "20261119030000", "timeText": "2026-11-19 03:00:00", "jsonSize": 1234000 }
  ]}
]}}
```

**`/Manage/restoreSystemData.do`**（POST，参数 `dataRoot`、`backupDir`，同步接口）

- 门禁与防护：
  - `isFirstAdminUserExists() == false` 才允许（与 `addFirstAdminUser` 同一信任窗口，初始化完成后接口自动失效）；
  - `redisEn == true` 时拒绝（集群模式共享库，禁止单点恢复）；
  - 静态 `AtomicBoolean restoring` 防并发重入；与 `addFirstAdminUser` 的互斥靠「先到先得 + 二次检查」兜底。
- 恢复步骤：

```
1. 校验：backupDir 必须位于 dataRoot/DocSysReposes/DBBackup/ 之下（防目录穿越），
   且 docsystem_data.json 存在且非空
2. 写数据根目录配置到 docSys.ini 用户配置副本（docSysIniPath/docSysConfig.properties：
   MxsDocDataRoot + 5 路径），沿用 applyDataRoot 的"拷贝→改"文件机制，
   但不落 WEB-INF/classes（留给启动初始化统一应用）
3. testDB 失败 → createDB()                       ← 覆盖「sqlite DB 文件被删」
4. rebuildDBSchema()：主表 drop 后按当前版本重建；附加表（system_setting/Agent 表）
   保留表结构仅清空数据（importFromJson 只插入不建表，直接 drop 会导致附加表内容丢失）
5. importDatabaseFromJsonFile(全表, backupDir, "docsystem_data.json")
6. 成功判据：isFirstAdminUserExists() == true（users 表有超管 = 数据真的进来了）
7. 调用 docSysInit(true)：
   - 入口完成 docSys.ini → WEB-INF/classes 配置拷贝（这就是"配置修改发生在启动初始化"）
   - 全局重初始化（数据路径/Redis/LDAP/LLM）+ checkAndUpdateDB + 定时备份任务 + Agent 初始化
   - 返回 "ok" 即整个恢复完成，无需重启 Tomcat
8. addSystemLog("系统数据恢复" 成功/失败)
```

- 失败处理（步骤 3~7 任一步失败）：
  - **清库回滚**：`deleteDBTabsEx + initDBTables` 重建空 schema——保证「全新启动」选项在任何失败后仍可用（否则半截数据会让 `addFirstAdminUser` 误判「管理员已存在」）；
  - 返回错误详情（原因 + 备份目录），前端展示后允许重选；
  - Log.info 落文件日志留痕。
- 成功返回：`{"status":"ok"}`（不回传任何账号信息，恢复后用原管理员账号登录）。

### 4.3 「数据库不存在」场景的入口修复（P1，独立小改动）

现状：sqlite 的 `DocSystem.db` 被删/为 0 字节时，启动 `testDB` 失败只写 `ERROR_DBNotExists`；随后 `getLoginUser` 查询直接抛「no such table」→ 前端只报「服务器异常」，首管入口出不来，恢复入口也就不存在。

改法：`docSysInit(false)` 中 sqlite 分支，`testDB` 失败时**自动 `createDB + initDB`**（嵌入式库、零外部依赖，把"文件不存在"归一化为"空库"），随后自然进入 `needAddFirstAdmin` 分支。mysql 缺库维持现有安装页路径（库在外部服务器，不能替用户建），超出本方案范围。

## 6. 关键设计决策

| 决策点 | 结论 | 理由 |
|---|---|---|
| 导入格式 | **一律 JSON**（SQL 不用于恢复） | JSON 导出/导入均为对象级、通用 JDBC，跨数据库类型安全（mysql 备份 → sqlite 新装）；SQL 是方言性 INSERT，跨库不可靠 |
| 只显示最新备份 vs 可选指定备份 | 默认选最新 + 可展开选任意备份 | 需求要求"失败后可选另一个数据恢复"（最新备份可能也损坏）；readBackupInfo 本来就遍历全部目录，返回列表几乎零成本 |
| 数据根目录配置如何生效 | 只写 docSys.ini 用户配置副本，由 `docSysInit(true)` 在启动初始化过程中拷贝应用 | 配置修改严格发生在"启动初始化"；复用现成机制（配置拷贝 + 全局重初始化 + 任务启动），无需重启 Tomcat，也不新增会话中直改 app 配置的路径 |
| 恢复是否需要重启 Tomcat | 不需要 | 同上：docSysInit(true) 会话内完成全部初始化；DB URL 在 jdbc.properties 且不动 |
| 旧版本备份兼容 | 无需迁移 | JSON 数据灌入当前版本空表 = DBUpgrade 同语义，缺列走默认值 |
| 同步还是异步接口 | 同步（前端长超时 + 进度动画） | 恢复目标是空库、一次全量 INSERT，sqlite 场景通常秒级；异步任务轮询机制留作后续大库场景升级 |
| 失败后状态 | 自动清库回空 schema | 保证「全新启动」选项在任何失败后仍可用，闭环"重新选择" |
| 安全窗口 | 仅 `isFirstAdminUserExists()==false` 时开放恢复 | 与 `addFirstAdminUser` 同信任级别；系统初始化后接口自然失效，不会被登录用户滥用清库 |
| 集群模式 | 直接拒绝恢复 | 共享库场景下单节点 wipe + restore 不可接受 |
| 入口形态 | index 页面级 radio 面板，非弹窗内嵌 | 按需求；首管弹窗及其 applyDataRoot 既有行为完全不动，回归面最小 |

## 9. 风险与后续扩展

- **大库恢复耗时**：同步接口对超大库可能超时；后续可切换 GenericTask 异步 + 轮询（前端 RESTORING 视图已按"耗时任务"设计，替换成本低）。
- **json 缺失的老备份**：仅 SQL 的历史备份不可恢复（跨库不可靠，明确放弃）；列表阶段已过滤，用户不会误选。
- **恢复源的隐蔽性**：扫描范围即现有 getCandidates 的固定基座（Win 全盘、Linux 常规目录），挂载在非常规路径的数据目录不进入恢复列表（备份必须挂在扫描到的根下）。
- **备份保留策略**：DBBackup 无限增长问题与本方案无关，恢复列表 UI 上限展示（如每根最多 50 条）防渲染压力。
