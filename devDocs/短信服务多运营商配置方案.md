# 短信服务多运营商配置改造方案

> 目标：管理后台「系统设置 → 短信服务」支持多运营商（云片 / 阿里云 / 腾讯云 / 自定义 HTTP），字段按运营商动态呈现、可在线测试发送；配置改存**数据库表**（不再是 properties，参考 ScholarOS 的 `SystemSetting`），并同步提供通用「系统参数」管理页；老调用方零改动可运行。
> 状态：**方案已定稿，待开工**。调研日期：2026-09-29。
> 参考实现：`D:\Dev\ScholarOS`（`prisma/schema.prisma` 的 `SystemSetting`、`src/server/api/routers/systemSetting.ts`、`src/server/services/homePageConfigService.ts`、`src/app/(admin)/admin/systemSettings/*`）。
> 调研范围：`src/com/DocSystem/commonService/`、`src/com/DocSystem/controller/{Base,User,Manage}Controller.java`、`WebRoot/manager/{main.js,tmpl/systemSmsConfig*.html}`、`docSysConfig.properties`（工程源 + dev 运行期两份）、`agent/config/DatabaseInitializer.java`、`spring-mybatis.xml`。

## 已确认决策（2026-09-29 用户裁定）

| # | 决策 |
| --- | --- |
| 1 | 首期**四家运营商全做**：云片 / 阿里云 / 腾讯云 / 自定义 HTTP |
| 2 | 配置**存数据库表**（字符串字段，可存 JSON / 分隔串等任意格式），参考 ScholarOS 的系统参数存储与管理 |

### 1.2 配置存储事实

- **双源结构**：`docSys.ini/docSysConfig.properties` 是权威源（部分 key 运行期只读它），`WEB-INF/classes/docSysConfig.properties` 是镜像；启动时 `docSysInit()`（`BaseController.java:14745-14762`）在 checksum 不一致时用 ini 覆盖 classes。
- 短信 3 个 key **不在** ini-only 名单内 → 走 `ReadProperties.read()`（类路径镜像），后台写入 classes **即时生效、无需重启**。
- **实测（2026-09-29）**：工程源 `src/docSysConfig.properties`、运行期 classes 镜像、dev 的 `C:\TomcatForDocSysDev\docsys\tomcat\webapps\docSys.ini\docSysConfig.properties` 三份都**没有** `smsServer/smsApikey/smsTplid`，只有遗留的 `sms_userId/sms_pwd/sms_companyId`（老 `SmsClientInterface` 用，已无调用方）。⇒ **当前短信全靠硬编码兜底值在跑**（含一名开发者的真实云片 apikey）。
- `docSys.ini/` 目录运行期才 mkdirs；`bannerConfig.json`（`ManageController.java:180-190`）是「ini 优先、classes 回落」的既有范例 —— 也正属于**本次要摆脱**的那类文件式配置（新方案改为数据库表，见 2.1）。

## 2. 方案设计

### 2.1 配置存储：数据库表（参考 ScholarOS `SystemSetting`）

#### 2.1.1 参考实现（ScholarOS）

```prisma
model SystemSetting {
  id         String   @id @default(cuid(2))
  name       String   @unique // 变量名称
  value      String            // 变量值（字符串，可存任意格式）
  remark     String?           // 备注，可粘贴填写
  createTime DateTime @default(now())
  updateTime DateTime @updatedAt
}
```

配套实现（本次对齐的目标能力）：

| 参考文件 | 提供的能力 |
| --- | --- |
| `src/server/api/routers/systemSetting.ts` | 列表（分页 + name/value/remark 模糊搜索）、按名取、create/update/delete、batchUpdate |
| `src/server/services/homePageConfigService.ts` | **点分命名空间**存 JSON（`home.hero`、`home.demo`…）+ `getXxxMap()` / `upsertBulk()`（单次事务） |
| `src/lib/adminJsonConfigValidation.ts` | 按配置名做 JSON 结构校验（应填对象 / 应填数组） |
| `src/app/(admin)/admin/systemSettings/{page.tsx,SystemSettingDrawer.tsx}` | 列表 + 右侧抽屉编辑 + 统计卡片 + 导出/导入 JSON + 清空（导入/清空需 DB 密码二次校验） |
| `src/server/services/aiModelGroupService.ts` | 运行期读取 + **TTL 内存缓存**（避免每次请求打库） |

#### 2.1.2 DocSys 侧落地方案

**新表 `system_setting`**（**不并入** `DBTabNameMap`，避免与 `ObjMemberListMap`/objType 索引强绑定；DocSysAgent 的 `agent_*` 表即此先例）：

| 列 | 类型（MariaDB / SQLite） | 说明 |
| --- | --- | --- |
| `id` | `BIGINT AUTO_INCREMENT` / `INTEGER PRIMARY KEY AUTOINCREMENT` | 主键 |
| `name` | `VARCHAR(128) NOT NULL` + `UNIQUE` | 配置名（点分命名空间，如 `sms.provider`） |
| `value` | `LONGTEXT` / `TEXT` | 配置值，字符串；JSON / 逗号分隔串 / 布尔串均可 |
| `remark` | `VARCHAR(1024)` | 备注（用途、来源、示例） |
| `create_time` | `VARCHAR(32)` | 创建时间（`yyyy-MM-dd HH:mm:ss`），**由应用层写入** |
| `update_time` | `VARCHAR(32)` | 更新时间，同上 —— **不用** DB 的 `CURRENT_TIMESTAMP`：SQLite 下它是 UTC，实测会让页面时间少 8 小时 |

**建表**：新增 `com/DocSystem/commonService/sysConfig/SystemSettingInitializer.java`，照 `agent/config/DatabaseInitializer.java` 的成熟做法：

- `isSQLite(conn)` **按 JDBC 元数据判方言**（不依赖 `DB_TYPE` —— 它可能尚未就绪，且是 `BaseController` 包级字段）；
- 缺表检测：SQLite 查 `sqlite_master`，MariaDB 查 `information_schema`；
- 建表：两套 DDL 常量数组（MariaDB / SQLite）+ SQLite 单独的 `CREATE INDEX`（SQLite 不支持内联非唯一索引）；
- 幂等（`CREATE TABLE IF NOT EXISTS`），可重复调用。

**调用时机**：`docSysInit()` 成功路径已有 `triggerAgentInit()`（`BaseController.java:14904-14919`，经 `ContextLoader.getCurrentWebApplicationContext().getBean(...)` + try/catch 兜底）。新增同款 `triggerSystemSettingInit()`，与 DocSys「数据库就绪后」同节奏。**不能**放进 `BaseFunction` 静态块（那时数据库尚未创建/初始化）。

**数据访问**：

- `com/DocSystem/dao/SystemSettingMapper.java`（该包已被 `MapperScannerConfigurer` 扫描，`spring-mybatis.xml:66`）+ `src/com/DocSystem/mapping/SystemSettingMapper.xml`（`classpath:com/DocSystem/mapping/*.xml` 已被扫描）。
- **不用 upsert**：MariaDB 与 SQLite 语法不兼容 → 统一「`selectByKey` → 命中 `update` / 未命中 `insert`」两步法（同 `AgentConfigRepository` 注释所述）。
- `com/DocSystem/service/SystemSettingService.java`（`@Service`，`spring-mybatis.xml:22` 扫描 `com.DocSystem.service`；控制器经父容器可见）：`getValue/getJson/getAll(search,page,limit)/set/setMany/delete`，含 JSON 解析与**短 TTL 内存缓存**（保存后立即失效）。

**配置项（点分命名空间，仿 `home.*`）**：

| name | value 格式 | 说明 |
| --- | --- | --- |
| `sms.enabled` | `true` / `false` | 短信服务总开关 |
| `sms.provider` | `yunpian` / `aliyun` / `tencent` / `custom` | 当前运营商 |
| `sms.signName` | 纯文本 | 短信签名（阿里云/腾讯云必填；云片写在模板内） |
| `sms.scenes` | JSON 对象 | `{"register":{"tplId":"1341175","vars":["code"]}, "resetPwd":{...}, "phoneVerify":{...}, "test":{...}}` |
| `sms.yunpian` | JSON | `{"apikey":"","endpoint":"https://sms.yunpian.com/v2/sms/tpl_single_send.json"}` |
| `sms.aliyun` | JSON | `{"accessKeyId":"","accessKeySecret":"","regionId":"cn-hangzhou","endpoint":"dysmsapi.aliyuncs.com"}` |
| `sms.tencent` | JSON | `{"secretId":"","secretKey":"","sdkAppId":"","region":"ap-guangzhou","endpoint":"sms.tencentcloudapi.com"}` |
| `sms.custom` | JSON | `{"url":"","method":"POST","paramNames":{"phone":"mobile","tplId":"tpl_id","tplVars":"tpl_value"},"successField":"code","successValue":"0"}` |
| `sms.options` | JSON | `{"timeoutMs":10000,"retry":0,"codeLength":6,"codeTtlMinutes":15}` |

上述各行拼起来，等价于原先设想的一份整包配置（便于对照理解）：

```json
{
  "enabled": true,
  "provider": "yunpian",
  "signName": "自由团队",
  "scenes": {
    "register":    { "tplId": "1341175", "vars": ["code"] },
    "resetPwd":    { "tplId": "1341175", "vars": ["code"] },
    "phoneVerify": { "tplId": "1341175", "vars": ["code"] },
    "test":        { "tplId": "1341175", "vars": ["code"] }
  },
  "providers": {
    "yunpian": { "apikey": "", "endpoint": "https://sms.yunpian.com/v2/sms/tpl_single_send.json" },
    "aliyun":  { "accessKeyId": "", "accessKeySecret": "", "regionId": "cn-hangzhou", "endpoint": "dysmsapi.aliyuncs.com" },
    "tencent": { "secretId": "", "secretKey": "", "sdkAppId": "", "region": "ap-guangzhou", "endpoint": "sms.tencentcloudapi.com" },
    "custom":  { "url": "", "method": "POST",
                 "paramNames": { "phone": "mobile", "tplId": "tpl_id", "tplVars": "tpl_value" },
                 "successField": "code", "successValue": "0" }
  },
  "options": { "timeoutMs": 10000, "retry": 0, "codeLength": 6, "codeTtlMinutes": 15 }
}
```

设计要点：

1. **每个运营商一个 key**：切换运营商不丢配置；UI 只展示当前选中的那个。
2. **`vars` 为有序数组**——同时满足腾讯云 `TemplateParamSet`（按序数组）、阿里云 `TemplateParam`（按名 JSON）、云片（`#name#=value`）三种变量表达；标准变量名统一为 `code`（所有场景都有），可选 `min`/`product`。
3. 未填写的运营商字段存空串；密钥按明文存库、明文回显（与邮件/数据库页一致，决策 6 不做掩码）。
4. 老 properties 的 `smsServer/smsApikey/smsTplid` **保留不删**，但仅作「首次启用时的默认数据」与回滚参考（决策 4/7/10）；**不再作为运行期配置源**。
5. **不需要**给新表加 `docsystem_SYSTEM_SETTING.json` 成员表（不进 `DBTabNameMap`，走独立 Mapper 手写 SQL）。

### 2.2 后端结构

**配置存储层（新，通用）**

```
src/com/DocSystem/entity/SystemSetting.java              实体（id/name/value/remark/createTime/updateTime）
src/com/DocSystem/dao/SystemSettingMapper.java           MyBatis 接口（com.DocSystem.dao 已被扫描）
src/com/DocSystem/mapping/SystemSettingMapper.xml        手写 SQL（selectByKey/selectAll/count/insert/update/delete）
src/com/DocSystem/service/SystemSettingService.java      通用读写 + 短 TTL 缓存 + JSON 解析
src/com/DocSystem/commonService/sysConfig/SystemSettingInitializer.java   建表（双方言、幂等、缺表检测）
```

**短信层（新）**

```
src/com/DocSystem/commonService/sms/
├── SmsConfig.java            配置 POJO（由若干 system_setting 行装配而成）
├── SmsConfigStore.java       读写 SMS 相关 key（默认值、老 properties 迁移、参数校验）
├── SmsScene.java             场景枚举 REGISTER / RESET_PWD / PHONE_VERIFY / TEST
├── SmsProviderType.java      运营商枚举（YUNPIAN/ALIYUN/TENCENT/CUSTOM：默认 endpoint、字段定义、展示名）
├── SmsSender.java            统一入口 send(scene, phone, vars) → SmsSendResult（开关、参数校验、耗时、脱敏日志）
├── SmsSendResult.java        success + providerCode + providerMsg + raw + elapsedMs
├── SmsProvider.java          接口：send(cfg, scene, phone, vars)
├── SmsHttpClient.java        统一 HTTP（超时/可选重试/表单/JSON/取回状态码+耗时）
└── impl/
    ├── YunpianSmsProvider.java      POST 表单
    ├── AliyunSmsProvider.java       RPC + ACS3-HMAC-SHA256 签名
    ├── TencentSmsProvider.java      POST JSON + TC3-HMAC-SHA256 签名
    └── GenericHttpSmsProvider.java  自定义 HTTP（同时兼容旧 smsServer 语义）
```

- **不引入新 jar**：签名仅需 `javax.crypto.Mac`（HmacSHA1/HmacSHA256）+ `commons-codec-1.9`（已在 `WEB-INF/lib`）做 Base64/Hex；HTTP 用 JDK `HttpURLConnection`（JDK8 已支持 TLS1.2），避免 okhttp/kotlin 依赖链。
- **SMS 配置不在静态块读取**：`SmsConfigStore` 必须是 Spring bean、按需读表（`BaseFunction` 静态块在数据库就绪前就执行，不能在那里碰数据库）。
- **兼容层**：`SmsService.sendSms(...)` 旧 8 参签名保留（`@Deprecated`），内部转 `SmsSender`，保证改造期新旧共存。
- **调用方改造**：
  - `UserController.sendVerifyCodeSMS()` → `smsSender.send(type==1 ? RESET_PWD : REGISTER, phone, {"code": code})`
  - `BaseController.verifyTelephone()` → `smsSender.send(PHONE_VERIFY, tel, {"code": "Verify"})`（**保持现状语义**，决策 5）
  - `BaseController.getSmsSendUri()/getSmsApikey()/getSmsTplid()` 保留方法名，内部改走 `SmsConfigStore`（仍为空时回落硬编码兜底）

### 2.3 运营商适配矩阵

| 项 | 云片 yunpian | 阿里云 aliyun | 腾讯云 tencent | 自定义 custom |
| --- | --- | --- | --- | --- |
| 必填字段 | apikey | AccessKeyId / AccessKeySecret | SecretId / SecretKey / SdkAppId | url |
| 签名 | 签名写在模板内容里 | `SignName` 必填 | `SignName` 必填 | — |
| 模板 | `tpl_id`（数字） | `TemplateCode`（`SMS_xxx`） | `TemplateId`（数字） | 参数映射 |
| 请求 | POST 表单 `apikey,mobile,tpl_id,tpl_value` | RPC：`Action=SendSms&Version=2017-05-25&PhoneNumbers&SignName&TemplateCode&TemplateParam(JSON)` | POST JSON：`PhoneNumberSet[],SmsSdkAppId,SignName,TemplateId,TemplateParamSet[]`（头 `X-TC-Action/X-TC-Version: 2021-01-11/X-TC-Region`） | 用户配置 |
| 端点 | `https://sms.yunpian.com/v2/sms/tpl_single_send.json`（海外 `us.yunpian.com`） | `dysmsapi.aliyuncs.com` | `sms.tencentcloudapi.com` | — |
| 成功判定 | `code == 0` | `Code == "OK"` | `Response.SendStatusSet[0].Code == "Ok"` | `successField/successValue` |
| 签名算法 | 无 | V3 `ACS3-HMAC-SHA256` | TC3-HMAC-SHA256 | 无 |
| 手机号格式 | 11 位、无前缀 | `+86`/`86`/无前缀 | E.164 `+86...`（自动补 `+86`） | — |
| 变量格式 | `#code#=1234`（名与值均 urlencode） | `{"code":"1234"}` | `["1234"]`（按 `vars` 顺序） | 按参数映射 |

> 字段名取自 2026-09-29 抓取的官方文档：云片《指定模板单发》(v2)、阿里云《SendSms 2017-05-25》、腾讯云《SendSms 2021-01-11》。

**落地节奏**（决策 1 = 四家全做，但按里程碑增量交付）：M1–M6 先把存储/通用服务/短信页/云片/自定义 HTTP 跑通（对应现网可用），M7 阿里云、M8 腾讯云随后并行补齐。每加一个运营商只需新增一个 Provider 类 + 枚举一项 + UI 字段块。

## 4. 存量系统兼容与迁移（重点）

> 前置事实：install 页只提供 `mysql` / `sqlite`（`WebRoot/web/install.html:71-73`）——**所有部署都有数据库**，不存在"无库模式"需要照顾；唯一的"无表"情形是**老库**（本版本之前建的库），由幂等建表器覆盖。

### 4.1 取值链：表是唯一权威源

```
system_setting 表（sms.*）
  → 仅当表内还没有任何 sms.* 行时：用 docSysConfig.properties 的旧值作「首次启用时的默认数据」一次性写入表
    → 硬编码兜底（JavaSmsApi.apikey / URI_TPL_SEND_SMS / "1341175"，决策 7）
```

三条硬规则：

1. **表是唯一权威源**：只要表内存在 `sms.*` 行，就**只读表**，不再看 properties。`null` 与**空串都按「未填」处理**（旧后台保存会写入空串，见 `ManageController.java:395-410`），缺项直接走硬编码兜底。
2. **properties 只是「首次启用短信服务时的默认数据」**：初始化时读一次并入库，此后完全不参与运行期决策 —— 因此**不存在"properties 与表不一致"这种状态**，也不需要比对/提示/覆盖按钮之类逻辑。
3. **读表异常不得外溢**：表不存在 / DB 不可用 / SQL 报错 → 记日志后按兜底链取值，**不能影响启动与发送**（升级期最关键的容错点）。

### 4.2 首次初始化迁移（一次性、幂等）

**触发点**：`docSysInit()` 成功路径的建表钩子内，紧随建表之后执行；**判据 = 表内还没有任何 `sms.*` 行**（`count(name LIKE 'sms.%') == 0`），满足才迁移。迁移与建表均幂等，多节点并发安全（`name` 唯一约束 + `select→insert`）。

| # | 存量状态 | 处理 |
| --- | --- | --- |
| 1 | 老库无 `system_setting` 表 | 先幂等建表（仿 `agent_*` 表做法）；建表失败也不影响启动，取值链自动兜底 → 短信照旧可用 |
| 2 | properties 有 `smsApikey`+`smsTplid`、`smsServer` 空 | 入库 provider=`yunpian`、`sms.yunpian.apikey`=旧值、`sms.scenes` 四场景**沿用同一个 tplid**（旧版三场景本就共用一个模板 ID） |
| 3 | `smsServer` 含 `yunpian.com` | provider=`yunpian`；endpoint **归一到 v2** `https://sms.yunpian.com/v2/sms/tpl_single_send.json`（不原样搬 v1，否则把 P7 一起继承） |
| 4 | `smsServer` 是第三方/自建地址 | provider=`custom`，`sms.custom.url`=旧值；`paramNames` 默认与云片同形（`mobile`/`tpl_id`/`tpl_value`） |
| 5 | 只有部分字段有值（半配置） | **只把有值的项入库**，其余留空 → 运行时缺项走硬编码兜底，页面标「未配置」 |
| 6 | 三个 key 全空（**实测 dev 环境即如此**，只有无调用方的 `sms_userId/sms_pwd/sms_companyId`） | **不写任何 `sms.*` 行**（保持"从未配置"），走硬编码兜底 + 页面「未配置」红字提示（决策 7） |
| 7 | 老前端 / 缓存页面仍传 `server/apikey/tplid` | `setSystemSmsConfig.do` 保留旧参数解析（判定规则同 #2/#4），直接写入表 |
| 8 | 集群多节点 | 迁移幂等 + `name` 唯一约束 → 并发不会重复写；表在 DB 中天然共享，仅各节点内存缓存有 TTL 延迟（保存后本节点立即生效，其它节点最长 60s） |
| 9 | 回滚到旧版本 | 旧版本不读表，只读 properties（仍是旧值，**从不回写**，决策 9）→ 回到旧行为；新配置用通用参数页**导出 JSON 备份** |

### 4.3 零人工迁移承诺

升级后**不需要任何手工 SQL / 手工备份 / 停机切换**：建表自动 → 首次初始化迁移自动（幂等，重启不会重复写）→ 之后固定读表。迁移写入的行在 `remark` 标明来源（例：`migrated from docSysConfig.properties @ 2026-09-29`），便于审计与定位。

### 4.4 properties 的角色（运维须知）

- 3 个老 key **永不删除**（保留回滚价值），但**不再是运行时配置源**。
- 因此升级后**手工改 `docSysConfig.properties` 不会生效** —— 它只在"表内还没有 `sms.*` 行"时充当一次性默认数据。短信页保留**一行静态说明文字**提示这一点（不查询、不比对、无按钮）。
- 要改配置：走后台「短信服务」页（结构化）或「系统参数」页（直接改表）。

### 4.5 接口与调用方兼容

- 旧接口签名全部保留：`SmsService.sendSms(rt, phone, server, apikey, tplid, code, type, content)`（`@Deprecated` 适配层）、`getSmsSendUri/getSmsApikey/getSmsTplid`（改走 `SmsConfigStore`，名字不变）。
- 回滚路径：清空 `sms.*` 表记录即回到"从未配置"状态（下次启动会重新按 properties 迁移一次；properties 也为空则走硬编码兜底）。

## 6. 验证方案

- **编译（必须）**：`javac -parameters -g -encoding UTF-8 -d WebRoot/WEB-INF/classes -cp "WebRoot/WEB-INF/classes;WebRoot/WEB-INF/lib/*" <改动文件>`。
  ⚠️ Spring 控制器**必须带 `-parameters -g`**，否则命名参数缺失 → 该控制器所有带命名参数的方法运行期 500（本项目已知踩坑）。编译产物**必须**落在 `WebRoot/WEB-INF/classes`，不得落源码树。
- **部署**：dev Tomcat junction 已就绪（`C:\TomcatForDocSysDev\docsys\tomcat\webapps\DocSystem` → `D:\Dev\DocSys\WebRoot`）。改 Java 后**先编译再**重启（`docsys_restart.bat`），就绪探测 `http://localhost:8100/DocSystem/`（Admin/Admin）。
- **自检**：`system_setting` 表内容（名称/值/备注）、`tomcat\logs\docsys.log` 中的脱敏发送日志。
- **建表验证**：SQLite（dev Tomcat 默认）与 MySQL 各验一次 —— 两条缺表检测路径（`sqlite_master` / `information_schema`）都要走到。⏳ MySQL 侧尚未实测（本机无 MySQL 实例）。
- ⚠️ **触发时机（实测踩坑）**：`docSysInit()` 由 `StartupListener` 挂在 **DispatcherServlet 子容器**的 `ContextRefreshedEvent` 上 → 重启后只 curl 首页（静态/JSP）**不会**触发；必须先访问任一个 `.do` 端点（如 `POST /DocSystem/User/getLoginUser.do`）才会执行 init。
- **探针目录** `%TEMP%\docsys_chk\`（编译类/探针不入库）：`SystemSettingProbe`（建表 DDL / CRUD / 唯一约束 / 时间本地化）、`MapperBindingCheck`（XML 语句 id ↔ 接口方法一致性）、`DropSystemSetting`（删表以验证“全新库建表”路径）。
- **首次迁移回归**：用老 properties 造 4 组样本（#2 云片、#3 云片 v1 地址、#4 自定义地址、#5 半配置），验证「一次性入库 + 表内只读表」；再造 #6 全空场景验证**不写入任何 `sms.*` 行**；重启一次验证幂等。
- **网络无关验证（默认路径）**：`TestSmsRequestBuild` 断言各 Provider 生成的 URL / 表单 / JSON / 签名（阿里云与腾讯云用官方文档示例向量比对），不依赖真实短信。
- **端到端（需用户配合真实手机号）**：后台填测试号 → 「发送测试短信」→ 手机收到；再走通一次注册/找回密码验证码。

**本轮发现的真实缺陷（已修）**

1. SQLite 的 `CURRENT_TIMESTAMP` 是 **UTC** → 时间列改为 `VARCHAR(32)`、由应用层写本地时间（否则管理页时间少 8 小时）。
2. `slf4j` 在本项目只输出到 stdout（`log4j.rootLogger=info,stdout`）→ detached 启动时日志直接丢失；核心组件改用 `com.DocSystem.common.Log`（写 `docsys.log`），运维可查。

**接口约定**：`getAll.do(searchWord, pageIndex, pageSize)` → `data[]` + `dataEx=总数`；`set.do(name, value, remark)`；`delete.do(name)`；`import.do(settings=JSON 数组字符串)` → `{total, success, failed, errors[≤10]}`。导出为**前端**行为（分页取全量 → `Blob` 下载 `{systemSettings:[...]}`，与导入格式互为往返）。

**服务端校验**：名称非空 / ≤128 / 仅 `[A-Za-z0-9._-]`；值非空 / ≤65535；备注 ≤1024（与表定义对齐，避免 MySQL 严格模式报错）；JSON 型配置（`sms.scenes`、`sms.yunpian`、`sms.aliyun`、`sms.tencent`、`sms.custom`、`sms.options`，以及任何 `*.json`）必须是合法 JSON **对象**。
