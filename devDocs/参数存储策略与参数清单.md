# DocSys 参数存储策略与参数清单

> **目的**：说清参数「存在哪、为什么这么放、什么时候生效、哪些地方处理方式不一致」——避免后续优化时误改或误删。
> **适用范围**：主仓库 `D:\Dev\DocSys`。**核对时间**：2026-10-06（依据当时源码，关键位置给 `文件:行号`）；**2026-10-10 更新**：补登记「仓库级配置文件」这一类（§一-1 的 ④、§2.1-D2、§2.2-8/9，起因 = 新增仓库级选项 `allowHiddenFile`）。

# 一、存储策略

## 1. 总体：三个全局存储位置 + 一个按仓库隔离的位置

| # | 存储位置 | 定位 | 维护方 | 生效时机 |
| --- | --- | --- | --- | --- |
| ① | `WEB-INF/classes/jdbc.properties` + `docSys.ini/jdbc.properties`（用户副本） | **数据库连接**——框架层，受 SSM 约束 | 部署/启动脚本 | **重启** |
| ② | `WEB-INF/classes/docSysConfig.properties`（系统默认）+ `docSys.ini/docSysConfig.properties`（用户修改） | **与框架无关的业务参数** | 后台管理页 | 立即 / 下次请求（少数须重启） |
| ③ | 数据库 `system_setting` 表（另有 Agent 专用 `agent_config` 表） | **结构复杂、需要统一管理的参数** | 后台管理页 | 保存即生效 |
| ④ | **仓库自己目录下的配置文件**（`<仓库位置>/<id>/data/**/*.txt`） | **按仓库隔离的仓库级设置**（不是全局参数） | 仓库设置页 | 保存后**下一个请求**（无缓存） |

> `docSys.ini` 目录本身是**为绕开 Tomcat / SSM 框架约束而设计**的：把「用户的修改」与「随升级包被替换的系统默认文件」分开放。
> ④ 与前三者不同：它的作用域是**单个仓库**（每个仓库一份，随仓库删除而消失），不是全站参数；因此既不进 ini、也不进数据库，而是**跟着仓库目录走**（见 2.1-D2）。

## 2. `jdbc.properties`：框架层，必须重启（用启动脚本规避）

- **为什么改 classes 下的不生效**：SSM 在容器启动时读它一次就固定住了——
  `src/spring-mybatis.xml:19` `<context:property-placeholder location="classpath:jdbc.properties" .../>`，
  `:29` c3p0 `ComboPooledDataSource` 用它建**连接池**。运行期改文件不会被重读。
- **设计方案**：改 **ini 目录下**的 `jdbc.properties`，由**启动脚本在启动 Tomcat 前**把它拷到 `WEB-INF/classes/`，再启动 Tomcat。
- **启动脚本确实做了这个拷贝**（源码在仓库外的发布脚本里，本机 dev 脚本同样有）：
  - `docsys_start.bat:31-40`：`ini/jdbc.properties` **存在才** `del` + `copy` 覆盖 `WEB-INF/classes/jdbc.properties`（在启 Tomcat 之前）；
  - `docsys_restart.bat:55`、`docsys_start_hidden.bat:26` 都是 `call docsys_start.bat` → **重启/隐藏启动同样先拷贝**；
  - **只拷 `jdbc.properties`**；`docSysConfig.properties` 不在脚本拷贝范围（它靠应用内同步，见 §一-3）。
- **应用内第二道保险**：`BaseController.docSysInit()` `:14756` 也会比对两份 `jdbc.properties` 的 checksum，不一致就拷贝并写 `docSysIniState=needRestart` —— **要求重启**（因为此时连接池已经建好了）。用于「没走启动脚本、直接起 Tomcat」的场景。
- **「有没有改文件立刻生效的办法？」**
  - **改文件本身不会触发 Tomcat 重启**：本部署 `server.xml:125` 只有 `autoDeploy="true"`、**未开 `reloadable`**，默认 `context.xml` 只监听 `WEB-INF/web.xml`。但如果运维把 `reloadable="true"` 打开、或把 `WEB-INF/classes` 加进 `WatchedResource`，**改 classes 下的文件会触发整个应用重载**（会话丢失）—— 这也是「不要直接改 classes」的一条保险理由。
  - 想「不重启就换库」技术上可行，但要自己实现：动态数据源（`AbstractRoutingDataSource` + 运行时重建 `ComboPooledDataSource`、重新初始化 `SqlSessionFactory`）或引入配置中心。**实现它要处理连接池、事务、正在执行的连接**，收益低、风险高 → 建议保持「改 ini + 启动前拷贝 + 重启」。
  - **换 SpringBoot 不会自动更好**：Boot 同样是启动期把配置读进 `Environment`；只是它生态里有现成入口（`@RefreshScope` + `/actuator/refresh`、或 Nacos/Config Server）去**主动触发 bean 重建**，代码量比 SSM 少，但依旧是「显式触发刷新」而不是「改文件自动生效」，连接池/事务的安全责任一样在业务侧。

## 3. `docSysConfig.properties`：业务参数，可立即生效

- classes 下是**系统默认值**，ini 下是**用户修改**。后台保存走 `setSystemInfo.do`：`classes → ini（基线）→ 改字段 → 回拷 classes`（`ManageController.java:1796` / `:1958`），保证两份一致。
- **不直接把参数写在 classes 下的两个原因**：
  1. **在线升级会替换整个 `DocSystem` 目录** → 写在 classes 里的修改会被新版本覆盖丢失；ini 目录不随升级替换 → 用户修改能保留。**（主要理由）**
  2. 担心直接改 classes 触发 Tomcat 重启 —— 本部署默认不会（见上），但取决于运维是否开了 `reloadable`/`WatchedResource`；不改 classes 就没有这个风险。
- **启动同步**：`docSysInit()` `:14777` 比对 ini 与 classes 的 checksum，不一致就用 **ini 覆盖 classes** 并当场重新初始化（`initLdapConfig`/`initLLMConfig`/`initSystemAllowedNetworkConfig`/`initRedis`/`initDocSysDataPath`）。
  与 `jdbc.properties` 不同：**它不在启动脚本的拷贝范围**，靠的就是这道应用内同步。
- **生效时机取决于「谁在读」**（这正是"同类参数处理不一致"的根源）：
  - **启动期静态读取**（改 ini 后须**重启**）：`language`、`allowedNetworkConfig`、`ldapConfig`、`llmConfig`、`systemCompressEncoding`（`BaseFunction` 静态块 `:334`）
  - **每次请求重读**（保存后**下一个请求即生效**）：`javaHome`、`tomcatPath`、`openOfficePath`、`maxThreadCount`、`redisUrl`、`redisEn`、`serverUrl`（`BaseFunction` 各 getter）
  - **保存时显式 apply 到内存**（**立即生效**）：`allowedNetworkConfig`、`ldapConfig`、`llmConfig`、`isOnlyOfficeUsed`、`officeEditorApi`、`redisEn`/`redisUrl`（`initRedis()`，必要时 `restartClusterServer()`）

## 4. 数据库 `system_setting`：复杂 / 结构化参数

- **为什么入库**：有些参数结构复杂（列表、多字段、JSON），塞进 `docSysConfig.properties` 就得**自己维护一套解析方案**，文件臃肿、扩展困难；入库后能用「系统参数」页统一管理，还能跟着备份/导入导出走。
- **迁移方向**：逐步把 `docSysConfig.properties` 里合适的参数迁进表（已有先例：`mail.*`、`sms.*`、`ldap.servers`、`agent_config.llm_models`）。
- **但 `docSysConfig.properties` 不会完全废弃**，因为它具备**本地化（per-node）特征**——MxsDoc 支持集群，有些参数必须每台不同：
  - **调试日志**：`docSys.ini/debugLogLevel`、`docSys.ini/debugLogFile`（看的必须是**本机**日志，入库会让所有节点互相干扰）
  - **集群自身的设置**：`redisEn` / `redisUrl` / `serverUrl`（Redis 地址、集群地址）
  - 其他仅本机有意义的：证书、`mxsdoc.conf` 的 `serverHost` 等
- `agent_config`（`scope` + `config_key` + `config_value`）是另一张 DB 表，属于「数据库存储」的另一种，专放 Agent 侧配置（提示词、工具开关、轮数、权限、系统级模型列表）。

## 5. 硬性约束（改代码前必须遵守）

1. **不要把 per-node 参数放进数据库**（日志调试开关、集群设置）—— 集群下会互相污染。
2. **不要直接改 `WEB-INF/classes` 下的配置文件**：升级会替换、且可能触发应用重载；用户修改一律落 ini 或数据库。
3. **复杂结构参数不要往 `docSysConfig.properties` 塞**：走 `system_setting` 存 JSON。
4. **启动期静态读取的键不得声称"保存即生效"**：要么补 apply 方法，要么在页面上写清"需重启"。
5. **同类参数必须用同一种处理方式**：新参数选一处存储 + 一种生效方式，并登记到 §二（避免再出现 `ldapConfig` 那种「键在文件、权威在库」的双轨）。

### D2. 仓库目录下的配置文件（per-repo，**不在 ini / classes / 数据库**）

**存储位置**：`<仓库存储位置>/<reposId>/data/**/<名字>.txt`（`Path.getReposPath(repos)` 之下），随仓库一起删除。**无缓存**：每次读文件 → 保存后下一个请求即生效，集群一致（各节点读同一份文件）。**只有超管（`User.type == 2`）能改**，非超管即使直接 POST 也被忽略。

| 参数（页面字段） | 文件 | 内容 | 读入口 | 写入口 |
| --- | --- | --- | --- | --- |
| `encryptType` | `<仓库>/data/encryptSetting/encryptConfig.txt` | 原文（如 `1`/`2`） | `BaseFunction.getReposEncryptConfig()` → `BaseController.getReposEx()` 挂到 `Repos` 实体 | `BaseFunction.setReposEncryptConfig()` / `removeReposEncryptConfig()`；`ReposController.addRepos.do` / `updateReposInfo.do` |
| `allowHiddenFile`（仓库设置「允许操作隐藏文件和系统文件」） | `<仓库>/data/hiddenFileSetting/hiddenFileConfig.txt` | JSON `{"allow":1}` | `BaseFunction.getReposHiddenFileConfig()` → `getReposEx()` 挂到 `Repos.allowHiddenFile` | `setReposHiddenFileConfig()` / `removeReposHiddenFileConfig()`；同上两个端点（值变了才写；关掉即删文件） |
| `versionIgnoreConfig`（版本管理忽略设置） | `<仓库>/data/versionIgnoreSetting/<path>/.ignore`（**一个标记文件一份**，不是单个 txt；扫描回建 map） | 空文件存在即"忽略" | `BaseFunction.initReposVersionIgnoreConfigEx()`（扫描目录）/ `getReposVersionIgnoreConfig()`（**内存 + Redis 缓存 + checksum 摘要判变更**） | `DocController.setVersionIgnore()` → `setReposVersionIgnoreConfig()`（含 redis 写入） |

> ⚠️ 同一类里 `versionIgnoreConfig` 与另两个**生效方式不同**：它有**内存 + Redis 缓存**（`BaseFunction:299` 的 `reposVersionIgnoreConfigHashMap` + `ReposExtConfigDigest`），靠 checksum 判变更后**异步重建**；`encryptType`/`allowHiddenFile` **无缓存**（每请求读文件）。改这三个中任何一个时，别把「无缓存」的结论套到另一个上。

**为什么要单独一类**：这几个设置的作用域是**仓库**而非全站——放 `docSysConfig.properties` 会全局串味、且多仓库无法各自取值；入库则要改 `repos` 表结构（mapper + JSON schema + 建表 SQL + `getDBTabListForUpgarde` 版本分支 + 手工 `ALTER TABLE`），成本高；而「跟着仓库目录走」天然按仓库隔离、天然随仓库删除、天然集群一致（各节点读同一份文件）。`allowHiddenFile`（2026-10-10 新增）就是照抄 `encryptType` 这条路。

**新参数怎么选**：作用域是**单个仓库** → 走 ④（照抄本表，需要缓存时再照 `versionIgnoreConfig`）；全站且结构简单 → ②；全站且复杂/需统一管理 → ③；framework/需重启 → ①。

## 2.2 ★ 同类存储但处理方式**不一致**的地方（重点复查清单）

1. **`ldapConfig` / `llmConfig` 是双轨**：键仍在 `docSysConfig.properties`，但**权威源在数据库**（`ldap.servers` / `agent_config.llm_models`），启动时用库渲染的串覆盖文件 → 与同文件里 `tomcatPath` 这类「文件即权威」不同，**手工改 ini 无效**。
2. **`mail.*` / `sms.*` 的 properties 旧键只剩"首跑播种"作用**：表内已有行后不再读文件（与同文件的「文件权威」相反）。
3. **生效时机三种并存**：立即生效 / 下次请求生效 / 重启生效（见 2.1-C 生效方式列）→ 新参数必须明确选一种并登记。
4. **日志配置不在 `docSysConfig.properties`**：而是 ini 目录下的 `debugLogLevel` / `debugLogFile` 两个**独立文件**（`BaseController:15667` / `:15695` 读；`setLogLevelToFile` / `setLogFileToFile` 写），保存后**内存立即生效**并落这两个文件；**刻意不入库**（集群下必须看本机日志）。
5. **键名大小写 / 别名不一致**：`systemLogStorePath`→`SystemLogStorePath`、`indexDBStorePath`→`DBStorePath`、`agentSkillStorePath`→`AgentSkillStorePath`、`salesDataStorePath`→`SalesDataStorePath`、`clusterServerUrl`→`serverUrl`。
6. **checksum 自动同步只覆盖两个文件**：`jdbc.properties` 与 `docSysConfig.properties`（`docSysInit` `:14756` / `:14777`）；ini 目录下其他文件（`debugLogLevel`、`mxsdoc.conf`、`version`、证书）**不参与**这套同步，各有自己的读写逻辑。
7. **按模型「高级参数」里的 `maxTokens`：2026-10-08 已接线**（此前是"只存不发"——本清单要盯的典型「同类参数处理不一致」）。
   链路：`agent_config.llm_models[].settings.maxTokens`（管理端「AI接入设置 → 编辑模型 → 勾「使用高级参数」→ maxTokens」）
   → `AgentLlmConfigStore.toLegacyString` 渲染进运行期 `llmConfig` 串 → `LLMConfig.settings`
   → `ResolvedLlmConfig.parseMaxTokens(...)`（兼容 `maxTokens`/`max_tokens`；非法/越界一律回落 null）
   → `LLMService.effectiveMaxTokens(resolved.maxTokens)` 覆盖请求体 `max_tokens`（6 处请求体全覆盖）；
   未配 → 回落全局 `llm.max-tokens`。
   ⚠️ **同一件事两种生效时机**：按模型值**保存即生效**（`save()` → `BaseFunction.applyLLMConfigMirror` 立刻刷新
   `systemLLMConfig`，工具链每请求经 `UserLlmModelService.toResolved` 解析），**不需要重启**；
   而全局 `llm.max-tokens` 是 **仅启动期**（§2.1-E）。改的时候别把两者当成一种。
   护栏：`TestTruncationContract#perModelMaxTokensWiring`＋`TestStreamChatChunks#testPerModelMaxTokensInRequestBody`（抓真实请求体断言）。
8. **仓库级设置（存储位置 ④）此前未登记，已补进 §2.1-D2**（2026-10-10）：`encryptType` / `allowHiddenFile` / `versionIgnoreConfig` 三者同类（都是"仓库目录下的配置文件"），但**生效机制不一致**——`versionIgnoreConfig` 有内存+Redis 缓存与 checksum 判变更，另两个每请求读文件。新增仓库级设置时**照抄 `encryptType`（无缓存）**即可，除非确实需要缓存。
9. **`allowHiddenFile` 的落地点分散、易漏**（2026-10-10 新增参数，记录以备复查）：它不像普通参数只在一处读——读有 1 处（`getReposEx`），**拦截面却有 20+ 处**（`BaseController` 的 `*RealDoc*` 全族 + `saveDocToRepos`、`DocController` 的下载/office/agent 族、websocket `BussinessController` 的分享/office 链接/CAD 链接）。复核时用「所有 `RealDoc` 调用点 + 下载/预览/Agent 写入口」为清单，不要只看 Controller 的 `*RealDoc*` 命名。

# 附：实现细节与排障（需要时再看）

## 附-1 两个副本的读法与同步方向

- `ReadProperties.read("docSysConfig.properties", key)` → 读 **classes 副本**（classloader 根）
- `ReadProperties.getValue(docSysIniPath + "docSysConfig.properties", key)` → 读 **ini**
- **启动**：`docSysInit()` 比对 checksum，不一致则 **ini → classes** 并当场重新初始化相关静态量
- **保存**：`setSystemInfo.do` **classes → ini（基线）→ 改字段 → ini → classes**

## 附-2 坑（实测）

1. **`undefined` ≠ "不改"**：jQuery 把 `undefined` 序列化成空串，而 `setSystemInfo.do` 只把 `null` 当"不改" → **必须按页白名单提交**（已有 `postSystemInfo()`）。
2. **手改 ini 后没重启就点保存 → 手改被冲掉**（保存第一步用 classes 覆盖 ini）。
3. **`ReadProperties.setValue` 用 `Properties.store()` 重写整个文件**：注释丢失、键顺序重排、值里的 `:`/`=` 被转义（如 `ldap\://`）。
4. **`system_setting` 有 60s 单条缓存**：绕过 Service 直接改库会读到旧值（走 `set()` 会失效缓存）。
5. **fastjson 会省略 `null` 字段**：接口回传里可能缺字段，前端一律 `|| ""`。
6. **空值 ≠ 未配置**：LDAP 清空 = 关闭 LDAP 登录；LLM 清空 = AI 未配置（都渲染成空串）。
7. **只读态判定完全依赖 `disabled`**：新增表单字段要同步补 `disabled="disabled"`。
8. **重启 dev Tomcat 会让会话失效**：接口验证前先重新登录，否则会误判成"改动没生效"。

## 附-3 相关机制（需要时查）

- **启动顺序**：`BaseFunction` 静态块读 ini → `docSysInit()`（ini/classes 同步、数据库检查）→ `triggerAgentInit()`（建表、拷技能、**用 `llm_models` 覆盖运行期**）→ `triggerSystemSettingInit()`（建 `system_setting` 表、短信/邮件/**LDAP 播种与覆盖**）。
- **集群**：`clusterDeployCheckGlobal_ConfigCheck` 会把 `DB_URL` / `ldapConfig` / `LLMConfig` / `OfficeEditor` 与 Redis 缓存值比对；**各节点必须同 `DB_URL`** ⇒ `system_setting` / `agent_config` 天然共享；但 ini/classes 是**每节点本地**文件，改完需各节点各自保存或同步 ini。
- **备份/导出/导入**：`ExtraDBTabNameMap = {system_setting}` + `AgentDBTabNameMap`（见 `buildExtraDBTabList()`）已纳入自动备份与导出；**ini 文件不在数据库备份里**（升级/迁移需单独拷 `docSys.ini` 目录）。
- **详细案例**：`devDocs/邮件服务多供应商配置方案.md`、`devDocs/短信服务多运营商配置方案.md`、`devDocs/LDAP配置改造方案.md`、`devDocs/Agent大模型接入设置改造方案.md`、`devDocs/系统参数表备份与导入导出方案.md`。
