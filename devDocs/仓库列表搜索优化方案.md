### 1.3 热循环里的日志（性能放大器）

`src/util/LuceneUtil/LuceneUtil2.java` 在**每命中/每词**都打 `Log.debug`：`multiSearch:845`（`was hit on indexLib`）、`collectHitTermInfo:904/929/960/962`、`caculateHitScore:991`、`getHitTermPosition:1023`。

## 2. 实测数据（2026-10-09 10:02–10:06，dev 8100，Admin，可访问仓库 20 个）

| 关键词 | 耗时 | 命中数 | 响应体 | 带摘要条数 |
|---|---|---|---|---|
| `合同` | **14.0 s** | 35 | 42 KB | 9 |
| `test` | **210.4 s（≈ 服务端 3 分钟强制上限）** | 898 | **497 KB** | 10 |

补充事实：
- **索引体量悬殊**：`C:/DocSysReposes/DocSysLucene/repos_5_RDoc` = **486 MB**（repo5 = "test" 仓库，索引了整棵 DocSys 源码树），其余仓库索引只有 65 B ~ 114 KB → 跨仓搜索的耗时**几乎全由单个超大索引仓库决定**，不是"仓库数量多"造成的。
- 日志增长：两次搜索期间 `tomcat/logs/docsys.log` 从 16.65 MB → **25.24 MB**（+8.6 MB），`docsys_console.log` 已 39.6 MB。
- 服务端日志（`docsys.log`）确认：`searchDoc reposId:null` 两条分别 10:02:56、10:03:10，与前端测到的 14 s / 210 s 对得上。

### P0 实测（2026-10-09，埋点 + 日志瘦身之后）—— **已推翻原推断，以此为准**

同关键词 `test`（20 个可访问仓库、898 命中）跑 3 次（curl，已登录；日志级别 dev=debug）：

| 运行 | 端到端 | 逐仓搜索（20 仓，含等待） | 排序 | **组装（含前 10 条摘要抽取）** |
|---|---|---|---|---|
| 1 | **39.0 s** | 2.66 s | 2 ms | **36.22 s** |
| 2 | 36.5 s | 5.37 s | 1 ms | **31.08 s** |
| 3 | 35.3 s | 1.68 s | 0 ms | **33.60 s** |

- 三段相加与端到端吻合（误差 <1%）⇒ 计时口径可靠
- 逐仓内部：repo5（876 命中）仅 **2011 ms** ⇒ **486 MB 索引不是问题**（"索引体量大拖满 3 分钟"的推断**被推翻**）
- 逐仓里"直查"（每仓 1 次 `docSysGetDoc` 探测）就要 **70~88 ms/仓**，20 仓 ≈ 1.5 s ⇒ 是逐仓耗时的主要成分（run3 逐仓 1.68 s ≈ 直查 1.5 s）
- 改造前同关键词 **210.4 s**（含部分冷缓存因素）→ 改造后 **35.3~39.0 s**；日志量 **13,650 行 / 8.6 MB → 1,671 行 / 0.18 MB（-98%）**

### 结论（对应问题 2）

**瓶颈是"组装 + 摘要抽取"，不是逐仓搜索，也不是 486 MB 的索引。**

1. **组装（含摘要抽取）= 31~36 s，占总时间 88~95%** ← 主因（`convertSearchResultToDocList` 前 10 条读整篇内容 + Office 文本抽取 + base64）
2. **逐仓搜索只有 1.7~5.4 s**；其中"直查"占大头（70~88 ms/仓 × 20）
3. 服务端不分页/无上限 → 影响响应体（549 KB）与内存，但不占主要时间
4. 热循环日志在 dev 下是最大单项（210 → 35 s 的主要来源）；生产 `info` 级下只余字符串拼接开销
5. 慢**不是**"仓库顺序搜索"（每仓并发线程，上限 10）

## 3. 竞品交互调研（设计依据）

| 产品 | 做法 | 我们可借鉴 |
|---|---|---|
| Google 搜索 / Google Drive | 结果区顶部「找到约 N 条（0.42 秒）」；服务端分页 | **显示命中数 + 耗时**，让"慢"变成可感知的信息 |
| GitHub 代码搜索 | 输入即搜（debounce）；结果**增量**出现；显示总数与耗时；可取消 | 增量渲染 + 取消 |
| VS Code 全局搜索 | 边搜边出结果；进度条显示「已搜 X / 共 Y 文件」；有停止按钮 | **进度比例**（我们天然有"逐仓完成"事件）+ 停止 |
| Gmail | 搜索时**保留旧结果** + 顶部细进度条，完成后替换；显示 `1–50 of N` | **不清空页面**（现在是一把清空 `#project-box`） |
| Slack | 搜索面板先出"快速结果"（频道/消息/文件分类型），慢的部分随后补 | **两阶段返回**：文件名/路径命中先出，内容命中后补 |
| Windows 资源管理器 | 地址栏进度条 + 停止按钮 + 增量结果 | 进度条 + 停止 |
| Notion / 语雀类 | 结果里的**摘要片段高亮命中词**，且片段以命中词为中心 | 摘要高亮 + 片段居中（问题 3） |
| 通用超时降级（搜索引擎/企业盘） | 到预算就出**部分结果**，文案明确"仍在后台搜索…" | 超时**如实提示**，而不是静默等 3 分钟 |

**三个选项**（请选一个）：
- **A. 级别前置 + 惰性拼接**：调用点改成 `if (Log.isDebugEnable()) Log.debug(...)`（或新增 `Log.debugLazy(...)`）。dev 仍能全量看、prod 不落盘也**不拼字符串**。改动面：11 个点，零功能风险。
- **B. 删掉逐词/逐位置日志，只留汇总**（每仓一条：命中数/耗时/词数；可保留 `multiSearch` 每命中一条）。日志体积降最多，但排查时信息少。
- **C. 保留 debug 但加采样**（如每仓只打前 20 条命中 + 总计数）。折中；需新增计数变量。

> 说明：三项都不影响搜索结果正确性（纯日志），但会影响 dev 排查体验，所以交给用户定。

1. **服务端不可取消**：客户端 abort 后服务端仍会跑完（日志实测：被放弃的 `test` 搜索仍完成，且与新的搜索并发→ `合同` 的逐仓阶段从安静时的 **2.7 s** 变 **23 s**，端到端 14 s 变 49 s）。取消只解决"用户等待"，不省服务端资源 → 需 P2-4 的预算/超时 + P2-2 把摘要抽取降下来。
2. 取消后不展示"已返回的部分结果"（当前接口本就不支持部分返回，变体 1 才能给到）。

### P2 后端吞吐（决定"能多快"）
1. **服务端分页 + 上限**：`pageIndex/pageSize` 已经声明但没用 —— 让 `searchDoc.do` 真正分页（默认 20/页，上限 100），响应只带当前页的摘要 → 响应体从 497 KB 降到 ~20 KB。前端 `showSearchResults` 改为请求式翻页（保持旧接口向后兼容：不传分页参数时行为不变）。
2. **内容抽取只做当前页**：把 `maxNumOfContext=10` 的整篇内容抽取从"响应前全量"改为"只对当前页命中做"，并**加超时/大小预算**（单篇 50 MB 上限太激进，建议按类型限制，Office 类优先用已抽取的文本缓存 `tmp/OfficeText/…`）。
3. **两阶段返回（体验关键）—— 分两个变体，本次先做变体 1**

   阶段划分：阶段 A `快结果`= 文件名/路径命中（`_DocName` 索引，极快）+ 计数 → 先渲染；阶段 B `慢结果`= 内容/备注命中（`_RDoc/_VDoc`）+ 摘要 → 追加。

   | 形态 | 做法 | 改动点 | 预估 | 风险 |
   |---|---|---|---|---|
   | **变体 1（本次实施）** | 复用 `searchDoc.do` 加 `scope=name/content` 参数，前端**发两次请求**：先 name 阶段渲染，再 content 阶段追加。**接口向后兼容**（不传 `scope` = 现状） | 后端：把 `searchInRepos():4878` 写死的 `HitType_FileName\|FileContent\|FileComment` 改成从 `DocSearchContext` 传（可参照 `BaseController:24944` 现成示范）+ name 阶段不抽内容；前端：两次请求 + 合并去重 + 阶段文案 | **~100–200 行 / 0.5–1 天（含 E2E）** | 低：不动线程模型、不加状态 |
   | 变体 2（本次不做） | 新增 `searchDocStart.do` + `searchDocPoll.do`（job 轮询）或 **SSE**，逐仓完成即回报 | 后端：`searchContext` 改成**有状态会话对象**（`searchId` + 增量结果 + TTL + 并发上限）；拆掉 `waitForEndOfAsyncSearch`/`threadCount`/`Syncclock` 这套为阻塞设计的等待；取消要能设 `stop`；前端：增量追加渲染 + 「已搜 X/20 仓」进度 + 取消；还要兼容 `project.js` 仓内搜索 | **2–4 天** | 较高：有状态搜索的内存/TTL、SSE 反代缓冲与断线（`proxy_buffering`/超时）、Lucene 查询本身不可中断（取消只能"不再合并结果"）、两个入口兼容 |

   ⚠️ 顺序关系：**P2-1/P2-2/P2-4 不解决首屏时延**（它们管响应体大小与超时可控），首屏靠 P2-3；在变体 1 落地前，靠 P1 的进度/取消先"安抚"。
4. **超时与预算**：单仓超时（建议 3 s）+ 全局预算（建议 10 s，可在系统参数里配）；到预算就**如实**回报「部分仓库未完成」而不是静默等 3 分钟；`waitForEndOfAsyncSearch` 的 3 min `retrySleepTime` 需要复核（现在是"睡 3 分钟再醒"）。
5. **超大索引仓库（已裁定：不排除）**：repo5 那种 486 MB 索引（索引了整棵源码树）**不做任何排除/过滤**。代码侧只做"如实告知"：结果头显示总耗时；若触发预算截断，明示"部分仓库未完成"。
6. **搜索范围（已裁定：保持"全部可访问仓库"）**：本页无"当前仓库"概念，不做"默认当前仓库"的改法；体验改善全靠 P1（进度/取消/保留旧结果）+ P2-1/2/4（分页、限量抽取、预算）。

### P3 高亮（问题 3）
1. **修字段错配**：`searchWordsRender` 的结果要落到模板真正渲染的字段上（摘要用 `content`，或统一改模板为 `info`）；标题保持现有高亮。
2. **摘要高亮**：后端在 `convertSearchResultToDocList` 里已经拿到命中位置（`hitDoc.termPositionsForRDoc/ForVDoc`）—— 可直接在**后端**把 snippet 生成成"命中词前后居中 + 带位置信息"的结构，前端按位置插 `<em>`；或后端返回 `[{start,end}]` 位置数组，前端在解码后的文本上高亮。
3. **多关键词**：支持空格分词（后端 `multiSearch` 已按词处理），前端逐词高亮（现只处理一个词）。
4. **安全**：模板用的是 `{{# }}`（不转义）→ 高亮标记必须在**转义之后**插入，避免文件内容里的 `<script>`/HTML 被当 HTML 渲染（当前 `{{# doc.content}}` 已有这个隐患，改造时一并修）。

## 6. 风险

- `searchDoc.do` 有**两个前端入口**（`projects.js` 跨仓、`project.js` 仓内），改接口/改字段必须同时兼容，否则仓内搜索回归。
- 前端模板 `{{# }}` 不转义 → 插入高亮标记时若顺序不对会引入 **XSS**（现已有隐患）。
- 流式/两阶段返回会改动**请求-响应模型**（新增 SSE 或 job 接口），Nginx/反代与超时配置需要一起看（README 里有反代大文件超时的先例）。
- 生产日志默认 `info`，P0 的"日志瘦身"对生产耗时改善有限 —— **不要把 dev 的 8.6 MB 结论直接当生产收益**。
- repo5 的 486 MB 索引是**数据问题**，代码侧只能"少扫"，根治要靠索引/忽略规则（产品口径）。
