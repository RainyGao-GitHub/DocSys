# 仓库列表页（projects）搜索优化方案

建立于 2026-10-09。**状态：调研 + 方案完成，等用户裁定后开工**（本次为纯只读调研，未改任何代码）。
工作卡：`DevAgentControl/CURRENT_STATE_projects搜索优化.md`。

用户诉求（原始三条）：
1. 搜索过程中**没有明确指示**（只禁用了搜索框），搜索慢时像卡住 → 调研其他产品，设计更友好的交互。
2. 搜索**很慢** → 查两件事：后台搜索接口性能、是否"仓库顺序搜索"。
3. 结果**只高亮了标题**，摘要内容命中未高亮 → 命中内容也要高亮。

### 1.1 前端（两个入口都打同一个接口）

### 1.3 热循环里的日志（性能放大器）

`src/util/LuceneUtil/LuceneUtil2.java` 在**每命中/每词**都打 `Log.debug`：`multiSearch:845`（`was hit on indexLib`）、`collectHitTermInfo:904/929/960/962`、`caculateHitScore:991`、`getHitTermPosition:1023`。
- dev 环境 `webapps/docSys.ini/debugLogLevel = 0`（debug）→ 全部落盘 + `System.out` 双写。
- 生产默认 `Log.info`（`BaseController.getLogLevelFromFile():15726`，文件不存在→info）→ 这些行**不落盘**，但 `Log.debug("..." + a + b)` 的**参数字符串仍会先拼接**（Java 先求值再调用），量级 = 命中数 × 数条 × 多条字段拼接。

## 2. 实测数据（2026-10-09 10:02–10:06，dev 8100，Admin，可访问仓库 20 个）

| 关键词 | 耗时 | 命中数 | 响应体 | 带摘要条数 |
|---|---|---|---|---|
| `合同` | **14.0 s** | 35 | 42 KB | 9 |
| `test` | **210.4 s（≈ 服务端 3 分钟强制上限）** | 898 | **497 KB** | 10 |

补充事实：
- **索引体量悬殊**：`C:/DocSysReposes/DocSysLucene/repos_5_RDoc` = **486 MB**（repo5 = "test" 仓库，索引了整棵 DocSys 源码树），其余仓库索引只有 65 B ~ 114 KB → 跨仓搜索的耗时**几乎全由单个超大索引仓库决定**，不是"仓库数量多"造成的。
- 日志增长：两次搜索期间 `tomcat/logs/docsys.log` 从 16.65 MB → **25.24 MB**（+8.6 MB），`docsys_console.log` 已 39.6 MB。
- 服务端日志（`docsys.log`）确认：`searchDoc reposId:null` 两条分别 10:02:56、10:03:10，与前端测到的 14 s / 210 s 对得上。

### 结论（对应问题 2）
慢**不是**"仓库顺序搜索"（每仓是并发线程，上限 10），而是四项叠加：
1. **单仓索引体量**（repo5 486 MB）在 10 线程里独占一路，能拖满全局 3 分钟预算；
2. **响应前把全量结果 + 前 10 条的整篇内容抽取都做完**（`getDocContent` 上限 50 MB/篇，Office 类文件还要走文本抽取）；
3. **服务端不分页、无上限**，把 898 条命中（497 KB）一次性吐出来，前端再客户端分页；
4. **热循环 debug 日志**（dev 全量落盘；生产虽不落盘但仍在拼字符串）。
另外 `hitDocSmartSearch` 的磁盘/远程探测（最多 6 次/仓）在 20 仓上是 0~120 次无谓 IO，值得单独核。

## 3. 竞品交互调研（设计依据）

## 4. 改造方案（分阶段，建议按 P0→P3 实施）

### P0 度量与止血（低成本，先做）
1. `DocController.searchDoc.do` 加阶段计时（`Log.info` 级别、单行汇总）：逐仓 Lucene 查询耗时、`hitDocSmartSearch` 探测耗时、内容抽取耗时、排序/组装耗时、命中数。
2. 前端加 `performance.now()` 计时，指哪慢打哪。
3. 热循环日志整改（`src/util/LuceneUtil/LuceneUtil2.java`）——**详细说明见下方"P0-3 热循环日志"**。
   - 验收：同一关键词（`test`）在 dev 下日志增量从 +8.6 MB/次降到 < 1 MB/次；耗时对比数字记入本方案。

#### P0-3 热循环日志（第 5 问的展开，**待用户裁定**）

**是什么**：`LuceneUtil2` 在"每个命中文档 × 每个命中词"的循环里直接调 `Log.debug(...)`，四类共 11 个点：

| 位置 | 内容 | 每个命中产生 |
|---|---|---|
| `LuceneUtil2.java:845`（`multiSearch`） | `multiSearch() [<docPath>] was hit on indexLib:<lib> hitType:<n>` | 1 行 |
| `:904`（`collectHitTermInfo` 入口） | `collectHitTermInfo() [<docPath>]` | 1 行 |
| `:929` / `:940` | 字段名 / 无词向量提示 | 0~2 行 |
| `:960` / `:962` | `命中[<词>], before/after hitScore[...]` | **单词命中 2 行** |
| `:991`（`caculateHitScore`） | `caculateHitScore() hitTermText:<词> newHitScore:<n>` | 单词命中 1 行 |
| `:1023`（`getHitTermPositions`） | `hitTerm pos[i] at [start,end]` | **每命中位置 1 行** |

外加 `BussinessBaseController` 里每条命中的 `setHitScore() hitDoc:...` 输出。

**实测代价**（dev，`debugLogLevel=0`）：
- 两次搜索（`合同` 14 s + `test` 210 s）共产生 **13,650 行**非空日志，其中 **11,360 行（83%）** 是上面这些热循环日志；`docsys.log` 体积 +8.6 MB
- `Log.debug()` 同时写 `docsys.log` 和 `System.out`（→ `docsys_console.log` 39.6 MB）
- 生产默认 `info`（`BaseController.getLogLevelFromFile():15726`，无 ini 文件时=info）：`Log.debug()` 内部先判级别、不落盘，但**调用处的字符串拼接已经发生**（Java 先求值实参）——量级 = 命中数 × 词数 × 多条字段拼接

**三个选项**（请选一个）：
- **A. 级别前置 + 惰性拼接**：调用点改成 `if (Log.isDebugEnable()) Log.debug(...)`（或新增 `Log.debugLazy(...)`）。dev 仍能全量看、prod 不落盘也**不拼字符串**。改动面：11 个点，零功能风险。
- **B. 删掉逐词/逐位置日志，只留汇总**（每仓一条：命中数/耗时/词数；可保留 `multiSearch` 每命中一条）。日志体积降最多，但排查时信息少。
- **C. 保留 debug 但加采样**（如每仓只打前 20 条命中 + 总计数）。折中；需新增计数变量。

> 说明：三项都不影响搜索结果正确性（纯日志），但会影响 dev 排查体验，所以交给用户定。

### P1 交互改造（前端，用户可感知的第一层）
1. **不再禁用输入框**：保持可输入可回车；用 `AbortController` 让**新搜索自动取消上一次**（现在只能等或刷新）。
2. **立即反馈**：点击/回车后 0 ms 先渲染「搜索中…」（骨架屏或细进度条），**保留旧结果**在下方（Gmail 式），不要清空页面。
3. **可感知进度**：每 1 s 刷新已耗时；若能拿到"逐仓完成"事件（P2 的流式接口），显示「已搜索 X/20 个仓库」。
4. **可取消**：>2 s 显示「取消」；取消后保留已返回的部分结果并标注"已取消（部分结果）"。
5. **结果头部**：显示「找到 N 条 · 用时 X.Xs」，并说明是否有仓库超时/未参与（见 P2-4）。
6. 文案与 `_Lang()` 同步（`projects.js`、`lang/ch.js`、`lang/en.js`）。

### P2 后端吞吐（决定"能多快"）
1. **服务端分页 + 上限**：`pageIndex/pageSize` 已经声明但没用 —— 让 `searchDoc.do` 真正分页（默认 20/页，上限 100），响应只带当前页的摘要 → 响应体从 497 KB 降到 ~20 KB。前端 `showSearchResults` 改为请求式翻页（保持旧接口向后兼容：不传分页参数时行为不变）。
2. **内容抽取只做当前页**：把 `maxNumOfContext=10` 的整篇内容抽取从"响应前全量"改为"只对当前页命中做"，并**加超时/大小预算**（单篇 50 MB 上限太激进，建议按类型限制，Office 类优先用已抽取的文本缓存 `tmp/OfficeText/…`）。
3. **两阶段返回（体验关键，工作量最大）**：<br>
   阶段 A `快结果`：文件名/路径命中（`DocName` 索引，极快）+ 计数 → 先渲染；<br>
   阶段 B `慢结果`：内容/备注命中（`RDoc/VDoc` 索引）+ 摘要 → 追加。<br>
   实现形态二选一：**SSE**（`searchId` + 逐仓事件）或 **job 轮询**（`searchDocStart.do` / `searchDocPoll.do`）。两者都需要前端配合，且要保持 `searchDoc.do` 老接口可用（`project.js` 仓内搜索仍在用）。
4. **超时与预算**：单仓超时（建议 3 s）+ 全局预算（建议 10 s，可在系统参数里配）；到预算就**如实**回报「部分仓库未完成」而不是静默等 3 分钟；`waitForEndOfAsyncSearch` 的 3 min `retrySleepTime` 需要复核（现在是"睡 3 分钟再醒"）。
5. **超大索引仓库（已裁定：不排除）**：repo5 那种 486 MB 索引（索引了整棵源码树）**不做任何排除/过滤**。代码侧只做"如实告知"：结果头显示总耗时；若触发预算截断，明示"部分仓库未完成"。
6. **搜索范围（已裁定：保持"全部可访问仓库"）**：本页无"当前仓库"概念，不做"默认当前仓库"的改法；体验改善全靠 P1（进度/取消/保留旧结果）+ P2-1/2/4（分页、限量抽取、预算）。

### P3 高亮（问题 3）
1. **修字段错配**：`searchWordsRender` 的结果要落到模板真正渲染的字段上（摘要用 `content`，或统一改模板为 `info`）；标题保持现有高亮。
2. **摘要高亮**：后端在 `convertSearchResultToDocList` 里已经拿到命中位置（`hitDoc.termPositionsForRDoc/ForVDoc`）—— 可直接在**后端**把 snippet 生成成"命中词前后居中 + 带位置信息"的结构，前端按位置插 `<em>`；或后端返回 `[{start,end}]` 位置数组，前端在解码后的文本上高亮。
3. **多关键词**：支持空格分词（后端 `multiSearch` 已按词处理），前端逐词高亮（现只处理一个词）。
4. **安全**：模板用的是 `{{# }}`（不转义）→ 高亮标记必须在**转义之后**插入，避免文件内容里的 `<script>`/HTML 被当 HTML 渲染（当前 `{{# doc.content}}` 已有这个隐患，改造时一并修）。
5. **片段质量**：没有命中位置时（如只命中文件名）应显示文件开头摘要并**不**高亮，或显示"命中文件名"标识；有位置时以命中词为中心取窗（现在无位置时直接取开头 1000 字）。

## 5. 验收口径（可量化）

| 项 | 现状 | 目标 |
|---|---|---|
| 首屏可见结果 | 14.0 s（`合同`）/ 210 s（`test`） | ≤ 1.5 s（阶段 A 快结果） |

## 6. 风险

- `searchDoc.do` 有**两个前端入口**（`projects.js` 跨仓、`project.js` 仓内），改接口/改字段必须同时兼容，否则仓内搜索回归。
- 前端模板 `{{# }}` 不转义 → 插入高亮标记时若顺序不对会引入 **XSS**（现已有隐患）。
- 流式/两阶段返回会改动**请求-响应模型**（新增 SSE 或 job 接口），Nginx/反代与超时配置需要一起看（README 里有反代大文件超时的先例）。
- 生产日志默认 `info`，P0 的"日志瘦身"对生产耗时改善有限 —— **不要把 dev 的 8.6 MB 结论直接当生产收益**。
- repo5 的 486 MB 索引是**数据问题**，代码侧只能"少扫"，根治要靠索引/忽略规则（产品口径）。
