# 用户管理：搜索部分匹配 + 排序选择 方案与实施记录

> 背景：客户反馈「用户管理里搜索必须输入完整值才搜得到，不友好」，并要求「增加排序选择（创建日期、用户名，升序/降序），默认最近创建的在前」。
> 状态：**已实施并通过验证（dev 8100 真实页面 + 接口级）**，等用户确认后提交。
> 涉及仓库：主仓库（`BaseController`/`ManageController`/`UserMapper.xml`/manager 前端）+ **websocket 仓库**（导出接口）。

## 1. 调研结论（全部有实测证据）

### 1.1 搜索"必须完整匹配"的根因：`like` 的参数没带 `%`

```
WebRoot/manager/main.js  showUserList() → POST /Manage/getUserList.do {userName, pageIndex, pageSize}
 → ManageController.getUserList.do:2833   把同一关键字塞进 User 的 name/realName/nickName/email/tel 五个字段
 → BaseController.getUserListOnPage:3213  user != null → 走 "Like" 分支（getCountWithParamLike + getUserListWithParamLike）
                                          user == null → 走精确分支（getCountWithParam / getUserListWithParam）← 无关键字时的默认列表
 → BaseController.buildQueryParamForObj:23130  反射取字段，**把原值直接放进 param，不拼 `%`**
 → UserMapper.xml queryUserWithParamLike:375 / getCountWithParamLike:353
        where 1 = 1 and ( NAME like #{name} or REAL_NAME like #{realName} or NICK_NAME like #{nickName} or EMAIL like #{email} or TEL like #{tel} )
```

`like 'Admi'`（无通配符）在 SQLite/MySQL 里等价于 `= 'Admi'` → 只有完整值命中。**改动前实测**（dev，5 个用户）：

| 关键字 | 命中 |
| --- | --- |
| `Admin`（完整）/ `admin`（大小写不同） | 1 / 1 |
| `Admi`（前缀）/ `dmin`（中间子串）/ `652055239`（邮箱前缀） | 0 / 0 / 0 |

SQL 层对照（直连库）：`like 'Admi'`→0，**`like '%Admi%'`→1**，`REAL_NAME like '%王%'`→1。

### 1.2 排序现状

- 两条列表 SQL **都写死** `ORDER BY NAME ASC, CREATE_TIME DESC`（`queryUserWithParamLike` 与 `queryUserWithParam`）→ 实测默认列表顺序 = **用户名升序**，与创建时间无关。
- 页面**没有「创建时间」列**（表头 `# 用户ID 用户名 角色 昵称 名字 手机 邮箱 网络限制 操作`），但**有「用户ID」列** ✅。
- 排序可靠性：`CREATE_TIME` 是 `VARCHAR(50)`，写入一律 `yyyy-MM-dd HH:mm:ss`（定长 19；dev 5/5 行合规、无空值）→ 字典序 = 时间序（`order by CREATE_TIME desc` 实测正确），但**`order by ID desc` 与它不完全一致**（历史/测试数据的 ID 与创建时间可能不同源）→ 裁定后改用 ID 排序，语义为「新增用户 ID 递增 = 最近创建在前」。

### 1.3 数据库与 SQL 可移植性（决定实现方式）

- **默认/dev 库是 SQLite**：`jdbc:sqlite:${catalina.home}/DocSystem.db`（dev 实际文件 `C:\TomcatForDocSysDev\docsys\tomcat\DocSystem.db`）；产品同时提供 MySQL（安装目录有 `mysql/`、`mysql_start.bat`）。
- ⇒ **不能用 `concat('%', #{x}, '%')`**（SQLite 没有 `CONCAT()`）→ **`%` 必须在 Java 侧拼进参数值**，SQL 保持 `like #{x}` 不变，SQLite/MySQL 通吃。
- 大小写：两库都"ASCII 大小写不敏感"（实测 `admin` 命中 `Admin`）→ 不需要处理；中文按原样匹配。
- 性能：`%kw%` 无法用索引 → 全表扫描；`user` 表规模小（dev 5 行、客户通常几十~几百行）→ 可接受。

### 1.4 mapper XML 有"双份"（实施必踩）

- `spring-mybatis.xml:55-58`：`mapperLocations = classpath:com/DocSystem/mapping/*.xml` + `classpath:mapper/*.xml`
  → **运行时加载的是 `WebRoot/WEB-INF/classes/com/DocSystem/mapping/*.xml`**，不是 `src/…`。
- 两份靠 Eclipse 构建同步（改前 MD5 一致）；`WebRoot/WEB-INF/classes` 被 `WebRoot/WEB-INF/.gitignore` 忽略（不入 git）。
- ⇒ 改 `src/com/DocSystem/mapping/UserMapper.xml` 后**必须复制到 classes**，否则重启也不生效。

### 1.5 影响面

| 位置 | 关系 |
| --- | --- |
| `getCountWithParamLike` / `queryUserWithParamLike` | 两处 SQL 条件必须一致（本次两处都加了排序片段） |
| `queryUserWithParam`（无关键字分支 = 默认列表） | **同样写死 ORDER BY**，必须一起改，否则默认列表排序不变 |
| websocket 仓库 `BussinessController.exportUserList:5332` | **导出用户同源**（`getUserList(user)`）→ 搜索/排序都会同步影响导出 |
| websocket 仓库 `BussinessController.getPreferLinkAccessUsers:1222` | 分享链接的「可访问用户」列表也用 `getUserListOnPage` → 同样变成部分匹配 + 默认按用户ID降序（一致，符合预期） |
| `GroupMemberMapper.xml:112` / `ReposAuthMapper.xml:334` | 用户组/仓库成员搜索有同样的「like 无通配」问题 → **本轮按裁定不动** |

## 3. 实现

### 3.1 后端（主仓库 `src/com/DocSystem/controller/`）

`BaseController.java`：

- 新增 `getUserListOnPage(user, pageIndex, pageSize, sortField, sortOrder, queryResult)`；**保留原 5 参重载**（委托新方法，sort 传 null）——因为 websocket 仓库的 `BussinessController:1222` 也在调它，不能改签名。
- 新增 `getUserList(user, sortField, sortOrder)`（导出用，无分页）；原 `getUserList(User)` 保留并委托。
- 新增 `addUserSearchAndSortParam(param, user, sortField, sortOrder)`：
  - **部分匹配**：对 `USER_SEARCH_FIELDS = {name, realName, nickName, email, tel}` 的值包 `%…%`（空值不包）。注释里写明"必须在 Java 侧拼 %，不能用 SQL 的 concat（SQLite 无 CONCAT）"。
  - **排序白名单**：`sortField ∈ {id, name}`（默认 id）、`sortOrder ∈ {asc, desc}`（默认 desc），转换后以 `sortField`/`sortOrder` 放进 param；**用户输入不拼进 SQL**。

`ManageController.getUserList.do`：新增请求参数 `String sortField, String sortOrder`，透传给 `getUserListOnPage`（日志里也带上排序值）。

### 3.2 mapper（主仓库 `src/com/DocSystem/mapping/UserMapper.xml`）

新增可复用的排序片段（**不出现 `${}`，全部是固定 SQL 片段**）：

```xml
<sql id="User_List_OrderBy">
  <choose>
    <when test="sortField == 'name' and sortOrder == 'desc'">ORDER BY NAME DESC, ID DESC</when>
    <when test="sortField == 'name'">ORDER BY NAME ASC, ID DESC</when>
    <when test="sortOrder == 'asc'">ORDER BY ID ASC</when>
    <otherwise>ORDER BY ID DESC</otherwise>
  </choose>
</sql>
```

- `queryUserWithParamLike` 与 `queryUserWithParam` 里写死的 `ORDER BY NAME ASC, CREATE_TIME DESC` 都替换为 `<include refid="User_List_OrderBy" />`。
- `ID DESC` 作第二排序键，保证同名顺序稳定。
- 改完**同步复制到 `WebRoot/WEB-INF/classes/com/DocSystem/mapping/UserMapper.xml`**（见 §1.4）。

## 5. 坑与注意事项

1. **不要用 SQL 的 `concat` 拼 `%`**：默认库是 SQLite，没有 `CONCAT()`；`%` 一律在 Java 侧拼。
2. **mapper XML 双份**：改 `src/…` 必须同步到 `WebRoot/WEB-INF/classes/…`，否则不生效。
3. **无关键字时会走另一条 SQL**：有关键字走 `queryUserWithParam`/`queryUserWithParamLike` 中的 Like 分支，无关键字走精确分支 `queryUserWithParam` → **两条 SQL 都要加排序**，只改一条会出现"搜索后排序变了、不搜索没变"。
4. **`getUserListOnPage`/`getUserList` 的旧签名必须保留**：websocket 仓库的 `BussinessController` 在与主仓库同一 classpath 下编译/运行，改签名会连带破坏它。
5. **表头/箭头在 tmpl 里 → 每次列表重渲染都会被重建**，必须在渲染回调里回填箭头（`updateUserSortUi()`），否则删/改用户后箭头会丢失。
6. 表头点击的排序规则：**点击当前排序列 = 反向；点击新列 = 该列默认方向**（用户ID 降序、用户名 升序）——如果希望"新列一律升序"或其他规则，改 `main.js changeUserSort()` 一处即可。
7. `ID 降序 ≈ 创建时间降序` 的前提是"新增用户 ID 递增"；历史数据（迁移/补录）可能不满足，dev 里就有 ID 与 CREATE_TIME 不同源的行（不影响功能）。

## 6. 未做 / 遗留
