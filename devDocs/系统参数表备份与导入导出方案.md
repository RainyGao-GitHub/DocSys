# 系统参数表（system_setting）的备份与导入导出方案

> 需求（用户 2026-09-29）：配置会逐步从 properties 迁到数据库的 `system_setting` 表，
> 因此它必须像仓库等表一样**纳入自动备份**，并在「数据库设置」页**支持导出与导入**，
> 以支撑系统迁移与灾后恢复。

## 1. 结论速览

| 项 | 现状 | 目标 |
| --- | --- | --- |
| 自动备份是否含 `system_setting` | ❌ 不含（只备份 `DBTabNameMap` 里的表） | ✅ 含 |
| 「数据库设置」页导出 | ⚠️ 只导出 `DBTabNameMap`，`system_setting` 被漏掉 | ✅ 含 |
| 「数据库设置」页导入 `.sql` | ✅ 原样执行整段脚本（无表过滤）→ 只要导出含它就自动可用 | ✅ 保持 |
| 「数据库设置」页导入 `.json` | ❌ 只按 `DBTabNameMap` 的表名取数组，额外表被静默忽略 | ✅ 含（同名合并） |
| 升级前 / 重置前 / 删除前备份 | ⚠️ 同上（漏） | ✅ 含 |
| 系统迁移（push 到目标机） | ⚠️ 同上（漏）；接收端 JSON 导入亦漏 | ✅ 含（websocket 仓库） |

**根因**：备份/导出的表清单来自 `BaseController.buildBackUpTabList()`（`BaseController.java:18911`），
它只遍历 `DBTabNameMap`（`BaseController.java:14603`）。
`system_setting` **有意不并入**该数组 —— `SystemSettingInitializer.java:31` 已写明：
`DBTabNameMap` 的下标与 `ObjMemberListMap` / `objType` 索引强绑定，新增表会破坏既有映射。

因此本次不改 `DBTabNameMap`，而是新增一条**按表名**（与 objType 索引解耦）的「附加表」通道。

## 2. 现状事实（含证据）

buildBackUpTabList(skipDocTab)              // 只含 DBTabNameMap（skipDocTab=true 时排除 DOCSYS_DOC）

复制到 defaultReposRootPath + "DBBackup/<time>/"        // 自动备份的落盘位置

### 2.3 `system_setting` 表本身

- 结构（`SystemSettingInitializer.java:45 / 57`，MariaDB 与 SQLite 双方言）：
  `id, name(唯一 `uk_system_setting_name`), value(LONGTEXT/TEXT), remark, create_time(VARCHAR32), update_time(VARCHAR32)`
  → 时间列是**字符串**，导出/导入无需类型转换，跨 SQLite/MariaDB 迁移无损。
- 读写服务 `SystemSettingService`：`getValue / set(select→insert/update 两步，规避方言差异) / seedIfAbsent / delete / getAll / countByPrefix`。
- 当前库内实际内容（dev 库，2026-09-29）：**9 行，全部是 `sms.*`**（用户保留的测试数据）；
  `mail.*` 尚无（邮件 M1 的种子迁移待验证）。

## 3. 方案

### 3.1 新增「附加表」清单（按表名）

```java
// BaseController
/** 不并入 DBTabNameMap 的表：按表名处理，与 objType 索引无关（见 SystemSettingInitializer 注释） */
protected static final String[] ExtraDBTabNameMap = { "system_setting" };
```

> **D1 ✅ 2026-09-29 裁定**：`system_setting` **与 `AgentDBTabNameMap`（`BaseController.java:14619`）一并纳入** ——
> Agent 表（LLM 配置/技能/会话）同样只存在于数据库、同样需要迁移，且已经是按表名的数组，接入成本≈0。
> 实现上遍历「`ExtraDBTabNameMap` + `AgentDBTabNameMap`」两个数组。

### 3.2 导出侧：`backupDatabase` 追加附加表

新增两个通用函数（纯 JDBC，不依赖 objType）：

- `exportExtraTablesAsSql(tabNames, path, name, encode, …)`
  `SELECT * FROM t` → 由 `ResultSetMetaData` 取列名 → 生成 `INSERT INTO t (c1,c2,…) VALUES (…)`；
  值与列名做转义（`'`→`''`、黑名单字符），`NULL` 输出 `NULL`；单引号转义与现有 `buildInsertSqlForObject` 保持一致的写法。
- `exportExtraTablesAsJson(tabNames, …)`
  同一套通用读取，输出 `system_setting: [ {列:值, …}, … ]` 追加进 `docsystem_data.json`。

要点：
- **`docsystem_data.sql` / `.json` 的既有格式不变**（只是在末尾多一段/一个键），老备份文件仍可导入 ✓。
- 自动备份落盘位置不变：`<defaultReposRootPath>/DBBackup/<time>/docsystem_data.{sql,json}` ✓。

### 3.3 导入侧：JSON 通道追加附加表（SQL 通道无需改动）

- `.sql`：`executeSqlScript` 原样执行 → 导出文件里已有 `system_setting` 的 INSERT 就会执行 ✓
  （❗但要注意与 3.4 的「同名覆盖」语义：裸 INSERT 遇唯一键冲突会失败，见下）。
- `.json`：`importDatabaseFromJsonFile` 在遍历 objType 之后，追加遍历 `ExtraDBTabNameMap`：
  取出 `system_setting` 数组 → 逐行按 `name` **合并写入**（存在则 update value/remark，不存在则 insert）。
  实现优先复用 `SystemSettingService`（root 容器 bean，用
  `ContextLoader.getCurrentWebApplicationContext().getBean(SystemSettingService.class)` 取，二进制静态方法内不可注入，
  与 `BaseController.triggerSystemSettingInit()` 同一套路）；取不到 bean 时回退「select→update/insert」的原生 SQL 两步法。
- 系统迁移接收端（websocket 仓库 `importDatabaseFromJsonFileForPushRepos`，`BussinessController.java:2729`）追加同样的处理。

### 3.4 导入语义

> **D2 ✅ 2026-09-29 裁定**：**参考原有的导入逻辑**，不为附加表另立一套语义。

即：与 objType 表完全一致 —— **逐行裸 `INSERT INTO`**；若与目标机已有行冲突（`uk_system_setting_name`），
**该行导入失败并记日志，其余行继续**（与 `executeSqlScript` 的 `stopOnError=false` 行为一致）。

- 灾后恢复到空库：全部行正常导入 ✓
- 导入到已有配置的库：同名键保持目标机原值（不覆盖、也不删除目标机独有键）
- 需要强制覆盖时，运维先自行删除目标行再导入（与其它表一致，不额外提供开关）

### 3.5 不改的东西

- `DBTabNameMap`（下标即 objType，绝不能动）。
- `docsystem_data.{sql,json}` 现有内容与格式。
- `backupDatabase` 的调用方签名（只加内部逻辑，不加参数）→ 6 个调用点零改动。
- `deleteDBTabsEx()`（`BaseController.java:19166`）**不删** `system_setting`：目前「重置数据库」后配置保留（D6 待确认）。

**关键设计**

- **不碰 `DBTabNameMap`**：只新增「按表名」的附加表通道（`ExtraDBTabNameMap`），objType 索引映射完全不变。
- **工具类独立**：原先把实现写进 `BaseController` 私有方法，导致离线单测无法进行
  （`BaseController` 的静态初始化依赖 Web 环境：`BaseFunction.<clinit>` → `getWebPath()` → NPE）。
  抽到 `com.DocSystem.common.DBExtraTabBackup` 后既不依赖该静态环境，也能被离线探针直接测。
- **SQL 字面量转义分方言**：SQLite 只做 `'`→`''`；MySQL/MariaDB 额外把 `\`→`\\`（且先转反斜杠）。
  不能复用既有 `convertToSqlValue`（它只做 MySQL 风格 `\'`，在 SQLite 上会写进多余反斜杠）。
- **JSON 导入用 PreparedStatement**：列名取自 JSON key，值走 `?` 占位，彻底规避手拼字面量的转义问题。

**已知限制（记录，未改动）**

- SQL 导入走 `executeSqlScript`（MyBatis `ScriptRunner`，`stopOnError` 默认 false → 遇错继续）。
  脚本按 `;` 拆分，因此**若某个配置值本身含 `;`**，该条 INSERT 可能被拆坏 —— 这是既有实现对所有表
  都存在的限制；需要严格安全时请用 **JSON 文件**导入（新增路径，走占位符，不受影响）。
- `docsystem_data.json` 里各表键名是**未加引号**的裸标识符（既有格式，fastjson 宽容解析），
  故用 grep 找 `"system_setting"` 会漏，实际键为 `system_setting:`。
- 系统迁移接收端（websocket 仓库）已同步支持附加表，但**未做运行时联通测试**（需两台实例），
  仅通过编译验证。


## 6. 风险

1. **明文凭据入备份包**：`DBBackup/**` 与导出 zip 将包含 `sms.*` / `mail.*` / LLM 密钥。
   备份目录当前在 `defaultReposRootPath` 下，需确认其访问权限（D3）。
2. **导入覆盖**：合并语义下同名键会被源端覆盖（迁移时是预期行为，误导入会改掉目标机配置）。
3. **大表**：`system_setting` 是配置表（行数极少），不会带来备份体积/耗时问题。
4. **方言**：新增 SQL 需同时兼容 SQLite（dev）与 MariaDB/MySQL（生产）；
   优先走 `SystemSettingService`（已做过两步法方言规避），只有写文件时才直接拼 SQL。
