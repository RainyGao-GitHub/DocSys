# DocSys 接口中文编码清单与约定

> 目的：把"哪些接口的中文是靠 URL 传的、会不会乱码"这件事一次盘清，供后续决定是否改 POST。
> 结论先行：**问题不在 GET/POST，而在"中文放在 URL 里还是 body 里"**。当前只有 11 个"必须用 URL"的接口依赖编码补丁（已打补丁），其余接口的中文全部走 POST body，不需要补丁。
> 盘点时间：2026-09-17（dev Tomcat 7.0.56 + 工作区源码）。
> 状态：盘点完成；**决策 = 暂不改动任何接口，仅记录**（2026-09-17）。下次若有人想"顺手把接口都改成 POST"，先看本文第 5、7 节——**没有必要**。

## 1. 判定规则（为什么会有这个差异）

| 中文所在位置 | 解码由谁决定 | 结果 |
| --- | --- | --- |
| **URL（query / path 段）** | Tomcat `Connector` 的 `URIEncoding`；本工程未配置 → Tomcat 7 默认 **ISO-8859-1** | 直接拿到会乱码（`中` → `ä¸`），需要 `new String(x.getBytes("ISO8859-1"),"UTF-8")` **补丁**；且整条请求行受 **8192 字节**限制 |
| **POST 表单 body**（`application/x-www-form-urlencoded`） | 请求字符集：Content-Type 的 charset，或 `web.xml` 的 `CharacterEncodingFilter(UTF-8)`（本工程已配置，映射 `/*`） | 正确，**不需要补丁** |
| **POST JSON body**（`application/json`） | JSON 规范强制 UTF-8（Jackson 按 UTF-8 解码） | 正确，**不需要补丁** |
| **HTTP 响应头**（如 `Content-Disposition` 文件名） | 头按 ISO-8859-1 处理 | 需要 `getBytes("UTF-8")→ISO8859-1` 的反向转换（`BaseController:2249`、`UserController:989`） |

⚠️ 前提条件：`URIEncoding` 依赖"整包发布（自带 Tomcat 7.0.56）"。若把 war 部署进 Tomcat 8.5+/9（默认 UTF-8）或给 Connector 配 `URIEncoding="UTF-8"`，A 类补丁会把中文打成 `????` —— 详见 `docs`/`devDocs/本地开发Tomcat部署与启动指南.md` 第 6-8 条。

## 2. A 类：中文必须走 URL 的接口（依赖补丁，共 11 个）

这些接口的调用方是**浏览器直接导航 / `<img src>` / 下载**等无法使用 POST 的场景，因此中文只能放 URL：

| 接口 | 方式 | 关键参数 | 补丁位置 |
| --- | --- | --- | --- |
| `/Doc/uploadDocEx/{vid}/{targetPath}/{targetName}/{authCode}/{shareId}` | POST（路径变量） | targetPath, targetName | DocController:1851/1860 |
| `/Doc/downloadDoc.do` | GET | targetPath, targetName | DocController:2842/2852 |
| `/Doc/downloadDocChunked.do` | GET（分块下载） | targetPath, targetName | DocController:2917/2925 |
| `/Doc/downloadDocEx.do` | GET | targetPath, targetName | DocController:3068/3078 |
| `/Doc/downloadVideo/{vid}/{path}/{name}/{targetPath}/{targetName}/...` | GET（路径变量） | path, name, target(Path/Name) | DocController:3157/3167 |
| `/Doc/downloadImg/{vid}/{path}/{name}/{targetPath}/{targetName}/...` | GET（路径变量） | path, name, target(Path/Name) | DocController:3259/3269/3320/3327 |
| `/Doc/downloadDoc/{vid}/{path}/{name}/{targetPath}/{targetName}/{...}/{fileName}` | GET（路径变量） | path, name, target(Path/Name), fileName | DocController:3439/3449/3529/3539 |
| `/Doc/downloadDocEx/{vid}/{path}/{name}/{targetPath}/{targetName}/...` | GET（路径变量） | path, name, target(Path/Name) | DocController:3620/3630 |
| `/Doc/downloadDocRS.do` | GET | name, path | DocController:4440/4450/4470/4554/4565 |
| `UserController getUserImg` | GET | fileName | UserController:989 |
| `/Doc/getVideoDocInfoWithConvertType`（视频转换，内部） | — | path, name（**base64**） | BaseFunction:6308/6315 |

补充事实：
- 下载类还有一条 **base64 变体**：`DocPreview.js` 直接把 `path`/`name` 以 base64 放进 URL（`downloadDoc.do?targetPath=Qzov...&targetName=44CK...`），用 ASCII 绕开编码问题 —— 说明历史上已经踩过这个坑。
- 这些接口的参数都是**文件名/路径**（短），不会撞 8192 字节请求行上限。
- **不建议改成 POST**：浏览器下载、`<img src>` 本来就只能用 GET。

## 3. B 类：中文走 POST body 的接口（不需要补丁，但"必须用 POST"是约定）

DocController / ReposController / UserController / ManageController 等约 **94 个**带文本参数（`path` / `name` / `content` / `commitMsg` / `userName` …）的接口属于这一类。它们能正常处理中文，**不是因为打了补丁，而是因为调用方一律用 POST 表单**：

| 抽查的调用点 | 传输方式 |
| --- | --- |
| `getDoc.do`（`project.js:1363`） | `type: "post"`, `data: {…path, name…}` |
| `renameDoc.do`（`renameConfirm.js:56`） | `type: "post"` |
| `getSubDocList.do`（`project.js:3710`） | `type: "post"` |
| `addDoc.do`（`addDoc.js:89`） | `type: "post"` |
| `updateDocContent.do`（`js/DocEdit.js:518`、`js/CommonEditor.js:308`） | `type: "post"` |
| `tmpSaveDocContent.do`（`js/DocEdit.js:195`、`js/CommonEditor.js:584`） | `type: "post"` |
| `querySystemLog.do`（`project.js:4865`） | `type: "post"` |

⚠️ **风险点（约定未被强制）**：这些接口在 Spring 侧多为 `@RequestMapping`（不限定 HTTP 方法），所以**用 GET 调也能进**，但中文会乱码。触发场景：第三方/开放 API 调用、新前端顺手写 GET、curl 调试。
可选加固（会破坏现有 GET 调用方，需先全量核对）：给这些接口补 `method = RequestMethod.POST`，让误用直接 405 而不是静默乱码。

## 4. C 类：长文本接口（重点看是否走 URL —— 已确认全部 POST）

长文本（正文/备注/日志）若走 URL 会先撞 8192 字节请求行上限（中文约 870 字）。已抽查确认调用方均为 POST：

| 接口 | 长文本参数 | 调用方式 |
| --- | --- | --- |
| `/Doc/addDoc.do` | content, commitMsg | POST |
| `/Doc/updateDocContent.do` | content, commitMsg | POST |
| `/Doc/tmpSaveDocContent.do` | content | POST |
| `/Doc/querySystemLog.do` | （检索条件） | POST |
| `POST /agent/stream`（Agent 对话，2026-09-17 新增） | command（可含整篇文章） | POST + JSON ✅ |

## 5. 结论与开发约定

1. **现状可用**：A 类（11 个）已打补丁且在"整包发布"前提下正确；其余接口中文全部走 body。
2. **新增接口规则（写进开发习惯）**：
   - **URL 里不放中文**（query / path 都不放）；必须放时（下载类场景）沿用现有补丁或在 Agent 侧用 base64/名称换 id。
   - 传中文一律 POST + body；大文本（>1KB）必须 body，避免 8192 字节请求行上限。
   - 返回字符串的接口要显式声明 charset（Spring 的 `StringHttpMessageConverter` 默认 ISO-8859-1）。
3. **可选的后续工作**（需要时再排期）：
   - 若将来要支持"把 war 部署到用户自备的新版 Tomcat"，先把 A 类补丁改成**条件式解码**（只在确实是 Latin-1 视图时才还原），再考虑给 Connector 配 `URIEncoding="UTF-8"`。
   - 若决定收紧，可给 B 类接口加 `POST` 方法限制（先全量核对调用方）。

## 6. 盘点方法（可复现）

1. `grep -n "ISO8859-1\|ISO-8859-1" src/com/DocSystem` → 定位所有补丁点（32 处），再按"最近的 `@RequestMapping`"归属到接口（本次结果见第 2 节）。
2. 遍历 `src/com/DocSystem/controller/*.java` + `agent/controller/*.java`，解出每个映射的签名参数，筛出文本型参数（`path|name|content|comment|…`）→ 105 个接口，其中 11 个带补丁。
3. 对"无补丁但带文本参数"的接口，逐个抽查前端调用点（`WebRoot/web/**/*.js` 里对应 `url:` 的 `type:` 是否为 post）→ 抽查全部为 POST。
4. 对长文本参数（`content`/`comment`/`query`）单独抽查调用方式 → 全部 POST。

## 7. GET 调用盘点（2026-09-17，只查未改）

> 目的：评估"给 B 类接口加 `method = POST` 限制"是否会破坏现有调用方。
> 结论：**当前没有被 GET 调用的文本参数接口**；已知调用方（前端 / Java 客户端 / 开放 API）全部 POST。

| 检查项 | 结果 |

| 前端 `$.ajax` 调用点 | 206 个，其中 `type` **非 post 的 = 0 个** |

### 7.3 结论与建议（未改代码）

- ✅ **可以**收紧：给 B 类"写操作"接口补 `method = RequestMethod.POST`，已知调用方不会被打断。
- ❌ **不要**收紧的对象：
  - 下载类（A 类，浏览器只能 GET）；
  - Agent 的 GET 只读接口（`/agent/sessions`、`/agent/models/list`、`/agent/skills`、`/agent/api/evolution/stats`、`/agent/sessions/{id}/messages`）；
  - 页面跳转类（`/User/tologin.do`、`pageTo.do` 等）。
- ⚠️ 未知调用方风险：第三方集成、客户自研脚本/书签、爬虫可能用 GET 直连只读接口。
  → 建议**先只收紧写操作**（add / update / delete / move / copy / rename / upload / import …），或先用 access log 观察一段时间再扩大范围。
