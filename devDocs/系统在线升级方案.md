# 系统在线升级方案

> 建立日期：2026-11-22。状态：**已实施（dev 联调完成，见任务卡 `DevAgentControl/CURRENT_STATE_系统在线升级.md` 的验证表；release 包 monitor 阶段全流程待用户环境验收）**。
> 实施纠偏（2026-11-22 实测）：① GitHub 线上 tag 实为 `DocSys_V2.02.91`（版本号带 `V` 前缀，本文原先写的 `DocSys_2.02.92` 不准，实现已做剥 V 处理）；② war 资产实际约 1.4GB（非"数百 MB"）。

## 1. 背景与目标

现状：系统升级需要用户手动下载 `DocSystem.war`，再进管理后台上传该 war 包升级（`Manage/upgradeSystem.do`），操作繁琐。

目标：首页导航栏为**超级管理员**显示"升级"按键——检测到新版本（GitHub Releases）时可一键在线升级：后台从 GitHub 下载最新 war 包后走**与后台上传 war 升级完全相同**的升级流程；升级期间按键显示"系统升级中..."，且该状态在用户刷新/重开页面后依然可见。

## 2. 现状调研结论（已核对源码）

### 2.1 现有 war 上传升级链路（可复用）

| 环节 | 位置 | 说明 |
|---|---|---|
| 管理后台入口 | `WebRoot/manager/tmpl/systemUpgrade.html` + `manager/main.js:4157`（`upgradeSystem`/`SystemUpgrade` 类） | 选 war 文件 → webUploader 分片上传到 `docSys.ini/upgrade/` → 调 `upgradeSystem.do(name,size)` |
| 升级执行 | `ManageController.upgradeSystem.do`（[ManageController.java:2708](../src/com/DocSystem/controller/ManageController.java)） | 超管门禁（superAdminAccessCheck）→ 文件名校验（须以 DocSystem 开头）→ `checkFileSizeAndCheckSum(upgradePath, name, size, null)`（BaseController:12130）→ 创建 LongTermTask → **解压 → 规整为 upgrade/DocSystem → NativeLibPruner 按平台裁剪 → 删 war → `createMonitorTrigger("upgrade")` → status=200** |
| 任务查询 | `queryLongTermTask.do`（按 taskId 查内存 longTermTaskHashMap）/ `stopLongTermTask.do`（stopFlag） | 页面刷新丢失 taskId → 无法直接复用，见 4.4 |
| monitor 执行 | 发布包 `docsysStartScripts/Windows/monitor_start.bat` + `docsys_upgrade.bat` | monitor 轮询 `docSys.ini/*.trigger`；发现 `upgrade.trigger` → **先删 trigger** → 备份旧 webapps/DocSystem → 用 `upgrade/DocSystem/` 替换 → 重启 Tomcat。**dev Tomcat 没有 monitor，trigger 不会被消费** |
| 版本号 | `WebRoot/version` 文件（如 `2.02.91`）；`getSystemVersion.do` 读取 | 版本比较可参考 `getVersionFromFile`（x.y.z 每段≤99 编码为 int） |

### 2.2 版本检测参考（mxs-doc-web 软件下载页）

`D:/Dev/mxs-doc-web/source/src/data/releases.ts`：

- **GitHub**：`https://api.github.com/repos/RainyGao-GitHub/DocSys/releases`，war 资产匹配规则 `/^DocSystem\.war$/i`（旧版回退 `DocSystem-C.war`），下载地址 `https://github.com/RainyGao-GitHub/DocSys/releases/download/<tag>/<file>`；tag 形如 `DocSys_V2.02.91`（**带 V 前缀**，实现剥 `DocSys_` 后再剥 `V` 得版本号）。
- **Gitee**：`https://gitee.com/api/v5/repos/RainyGao/DocSys/releases` 只有版本列表与说明，**无 war 资产**；且注释明确"GitHub 有时比 Gitee 晚一个版本"。
- 匿名 API 有限流：GitHub 60 次/h/IP（实测本机已超限过），Gitee 也有。→ 检测结果必须做服务端缓存。

### 2.3 检测源策略（2026-11-22 用户裁定：Gitee 优先）

发布流程：版本先发 Gitee（国内可达），war 稍后才传 GitHub（1.4GB 上传耗时）。GitHub 在国内经常整体不通——若检测依赖 GitHub，会出现"已发新版但用户看不到升级按键"的困惑。

裁定：**检测先查 Gitee（仅取版本号，Gitee 无 war 资产）→ Gitee 不可用再 GitHub 兜底（含 war 资产信息）；在线升级下载固定走 GitHub**。代价与接受度：GitHub war 未同步的窗口内点击升级会得到明确提示"新版本 x.y.z 的安装包尚未同步到GitHub"；GitHub 不通时点击升级报"无法访问GitHub"——按键能显示、失败时机后移，比检测不到更合理。

## 3. 总体流程

```
首页加载(pageInit) ──登录超管？──否──▶ 按键不显示
        │是
        ▼
  getUpgradeTask.do（新）──升级中？──是──▶ 按键显示"系统升级中..."（轮询）
        │否                                     │
        ▼                                       │
  checkSystemUpgrade.do（新，结果缓存10分钟）     │
        │有新版                                 │成功/失败后恢复
        ▼                                       │
  按键显示"升级(2.02.92)" ◀────────────────────┘
        │点击
        ▼
  确认框（版本/大小/将自动重启提示）→ POST onlineUpgrade.do（新）
        │返回 LongTermTask
        ▼
  按键"系统升级中..." + 轮询 queryLongTermTask.do（下载中xxMB→解压→裁剪→等待升级）
        │status=200（trigger 已创建，交给 monitor）
        ▼
  前端保持"系统升级中..."（期间 monitor 替换 webapps 并重启 Tomcat，接口短暂不可用）
        │重启完成
        ▼
  轮询恢复 → getUpgradeTask=false 且 checkSystemUpgrade=已最新 → 按键消失（提示刷新）
```

## 4. 后端设计（ManageController + 少量重构）

### 4.1 重构：抽取共用升级执行段（T1）

把 `upgradeSystem.do` 中"校验通过之后"的部分（解压→规整→裁剪→删包→trigger→200）抽为：

```java
//war 包已就位于 docSys.ini/upgrade/<warName> 后的升级执行流程（上传升级与在线升级共用）
protected void executeWarUpgrade(String warName, LongTermTask queryTask)
```

`upgradeSystem.do` 调用点行为不变（回归即可）；`onlineUpgrade.do` 下载校验后调用同一方法——满足"升级部分代码和后台上传 war 包完全一样"。

### 4.2 `checkSystemUpgrade.do`（新，超管）（T2）

- **检测顺序（2026-11-22 裁定，§2.3）**：先 Gitee `releases?per_page=5&direction=desc`（非 prerelease/draft、tag 剥 `DocSys_`/`V` 可解析 → 仅取版本号）→ 成功即用（**完全不碰 GitHub，节省其匿名配额**）；Gitee 不可用再 GitHub（`releases?per_page=5`，Accept vnd.github+json，超时 10s）→ 第一个非 draft 且资产含 `DocSystem.war`（回退 `DocSystem-C.war`）的 release。
- 与本地版本（version 文件）按 `getVersionFromFile` 同款编码比较（本地版本每次现读，降版本文件立即生效）。
- 返回 `{hasNewVersion, currentVersion, newVersion?, downloadSize?, source}`；downloadSize 仅 GitHub 源可知（Gitee 源省略，前端确认框相应不显示大小）。
- **两路独立静态缓存**（各 10 分钟成功 / 2 分钟失败）；GitHub 403/429 限流与网络不通分开报错。

### 4.3 `onlineUpgrade.do`（新，超管）（T3）

- **下载源固定 GitHub**（war 只在 GitHub）：取 GitHub 最新含 war 的 release（走缓存）；GitHub 不可达 → "无法访问GitHub（检查网络或代理）"（限流单独文案）——这是用户裁定的报错时机（检测可能来自 Gitee，按键已能显示）。
- GitHub war 版本 <= 本地时的细分：Gitee 目标版本 > 本地 → "新版本 x.y.z 的安装包尚未同步到GitHub，请稍后再试"（Gitee 先行、war 上传中的窗口）；否则 → "当前已是最新版本"。
- 防重入门禁 + 创建任务整体 `synchronized(upgradeGateLock)`（与 upgradeSystem.do 互斥）；创建 LongTermTask（type `onlineUpgrade`）后立即返回 taskId，后台线程执行：
  1. **下载**（status 自定义 0 下载中）：流式写到 `upgrade/DocSystem.war.downloading`，task.info 每 1~2s 更新"已下载 xxMB/总大小"；connect/read 超时；检查 stopFlag（支持 stopLongTermTask.do 取消）；完成后大小校验（资产 size，复用 `checkFileSizeAndCheckSum`）→ 改名 `DocSystem.war`；失败清理临时文件，status=-1。
  2. 调 `executeWarUpgrade("DocSystem.war", task)`（沿用其 1解压/2检查+裁剪/3创建升级任务/200 状态码语义）。

### 4.4 `getUpgradeTask.do`（新，超管）（T4）——跨刷新/跨重启的"升级中"判定

组合三路信号返回 `{upgrading, taskId?, status?, info?, phase}`：

1. **内存任务扫描**：longTermTaskHashMap 按 type 扫升级任务，未终态（status 非 200/-1，或 200 但 trigger 仍在）→ `phase: "prepare"`；
2. **`docSys.ini/upgrade.trigger` 存在** → `phase: "monitor"`（monitor 替换 webapps/重启中；monitor 响应时会先删 trigger 再执行，重启期间接口不可用——前端对接口失败按"仍升级中"处理）；
3. 都无 → `upgrading: false`。

### 4.5 升级能力判定（安装器部署门禁，2026-11-22 用户两次裁定后定稿：仅 deployType 标记）

**背景**：安装器部署（Windows/Mac 安装程序）没有 monitor 看门狗——`upgrade.trigger` 创建后无人消费，系统会永久卡在"系统升级中"并锁死后续升级，因此升级功能（首页在线升级 + 管理后台上传升级）需要禁用。

**判定（唯一依据）**：`docSys.ini/deployType` 文件内容为 `setup`（新安装器安装时写入）→ 禁用，提示"安装包部署不支持在线升级，请下载新版安装包升级"；其余一律放行。

**为什么不用 monitor.pid 存活检测（2026-11-22 二次裁定放弃）**：包脚本/monitor 不随 war 升级更新（docsys_upgrade 只替换 webapps）——存量用户网页升级到新版后跑的仍是老包 monitor，其是否写 pid 不可考（`WebRoot/web/sales` 整目录 gitignore，脚本在仓库外维护）；pid 检测一旦误判会把主流网页升级路径**永久锁死**。标记方案零误伤：被禁的恰好就是确实不能升级的安装器部署；代价是"zip 包手动起 Tomcat 无 monitor"的用户回到可能卡"升级中"的现状（用户裁定可接受，卡住时删 trigger 可自救）。

| 层 | 行为 |
|---|---|
| UI 门禁 | `checkSystemUpgrade.do` 返回 `upgradeSupported:false + upgradeDisabledReason`（早退，不消耗 Gitee/GitHub 配额）→ 首页按键隐藏；管理后台"系统升级"按钮禁用 + 红字原因（渲染后回调 `bindSystemUpgradeSupportCheck`） |
| 接口门禁 | `onlineUpgrade.do` / `upgradeSystem.do` 认证后第一步硬拒（防绕过；上传升级若等用户传完 1.4GB 才被拒体验太差，故入口先禁） |

**安装器侧要求**：只有"确认无 monitor 的安装器变体"才写 `deployType=setup`——Mac 控制台设计带 monitor 看门狗（能消费 trigger），Mac 安装器**不应**写（Windows 安装器应写）。

**遗留**：安装器构建工程需实现安装时写 `deployType=setup`（实现前门禁不生效=现状行为，无回归）；manager 的"重启服务"（restart.trigger 同样依赖 monitor）未纳入本期门禁，可后续同机制扩展。

## 6. 边界与风险

| 风险 | 处置 |
|---|---|
| GitHub 国内不可达/慢 | 检测与下载均设超时与明确报错；下载进度可见、可取消、可重试；镜像配置列为后续任务 |
| GitHub 匿名 API 限流（60/h/IP） | 服务端缓存 10 分钟，仅超管触发 |
| war 数百 MB 下载中断 | `.downloading` 临时名 + 完成后改名 + 大小校验 + 失败清理 |
| 升级中重复触发 | onlineUpgrade/upgradeSystem 共用防重入门禁（内存任务 + trigger 双判） |
| dev Tomcat 无 monitor | 在线升级会停在"等待升级"（trigger 无人消费）——与现有上传升级在 dev 的行为一致；dev 联调验证到 status=200+trigger 创建为止，全流程在 release 包验证 |
| 升级期间服务重启、接口不可用 | 前端接口失败按"升级中"保持，恢复后按版本重判 |
