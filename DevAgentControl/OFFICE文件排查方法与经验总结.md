## 三、本会话踩过的坑（防再踩）

0. **服务端打开链 `checkFileFormat=false`**（OfficeBase.convertOfficeFileToBin 内显式关闭）：转换方向**完全**由 `detectActualFormat + getOfficeFileType/getOfficeCanvasType(ext)` 决定，FileConverter 内部 `isOfficeFile` 的内容检测改写**不参与打开链** ⇒ 一切「假扩展名」类问题必须修**上层 detectActualFormat**；只修 COfficeFileFormatChecker 对打开链无效（但可消除其他 checkFileFormat=true 路径的盲区，本例两处都修了）。
1. **WebRoot/WEB-INF/classes 里的旧测试 class 优先于 test/bin**（DiagTiming 曾因此假复现）——测试前 `rm WebRoot/WEB-INF/classes/com/.../test/你的测试类.class`
2. **Git Bash sed -i 会把 CRLF 全改 LF** 污染整文件 → 用 perl -pi（字节级保留）或 python hex 转义（`\x22\x5c`）替换；替换后必 git diff 验证只动了目标行
3. **python 重写代码块时拼接偏移量错误**吃掉相邻代码（cessUser.do 事故）→ 大块重写后必 grep 相邻方法的注解完整性
4. **sdkjs 前后端共用**：sdk-all.js 浏览器也加载，绝不能通过隐藏/删除它来制造服务端失败
5. **触发保存失败的正确方法**：破坏部署目录 `server/FileConverter/bin/DoctRenderer.config`（把某 file 行指向 .NOTEXIST，备份 .testbak）——只影响服务端 apply_changes，前端/打开不受影响
6. **Eclipse 环境**：它用自己的 ECJ 构建+publish；我 javac 到工作区 classes 后，需用户在 Eclipse touch 源文件（触发 ECJ 重编）+ 重启 Tomcat 才真正生效
7. **保存链 changes 数据在** `OfficeEdit/<docId>/<dockey>/orgChanges/`（保存失败时移入 ErrorChanges<时间>/ 归档）
8. _Lang() 只支持 3 参（str1,connectStr,str2），多参调用被静默截断——多段文案直接用 + 拼接
9. **x2t.exe 退出码不可靠**：连打印 usage 都返回 88，转换成败只能看产物文件是否生成；交叉验证优先用**双参数形式** `x2t <in> <out.bin> <fontDir>`（按扩展名定方向，已验证可用）——params.xml 形式对**部分方向可用**（2026-11-20 实测 257→513 xlsx→PDF 可用出完整产物；早前"无输出无产物"是别的方向，遇到双参数不识别方向如 →PDF 时可先试 params.xml）。
10. **大小写敏感匹配是格式检测的常见盲区**：C++ `std::string::find`/Java `indexOf` 都敏感，而真实文件头大小写不定（本例 `Multipart/related`）。修法：两侧统一 toLowerCase（⚠️ 目标串也要小写——只转一侧反而把原本能匹配的弄坏，本例实测踩过）。
11. **位运算符移植陷阱：`>>` vs `>>>`**：C++ `unsigned` 的逻辑右移移植成 Java 必须写 `>>>`（`>>` 对负数符号扩展）。先例：GetIntFromBits 的 `0xFFFFFFFF >> n` 掩码恒全 1 → 位域提取退化裸右移（DTTM 日期 2025→3049）。**任何 0xFFFFFFFF/位掩码表达式 grep 一遍 `>>`**。
12. **CRLF 文件别用整文件重写工具改单行**（Edit/python 文本模式都会把 CRLF 统一成 LF，制造整文件假 diff）——用 python **二进制模式**（rb/wb）字节级替换；改后必 `git diff --stat` 核对变动行数（本例 TrackRevision 610 行假 diff 教训）。
13. **XLS 链"假成功"鉴别**：bin 体积远小于 C++ x2t 产物（28KB vs 675KB）= 内容全丢（NPE 被 readChild catch 吞掉不报错）——**xls 文件必须对比 bin 体积/正文关键词**，ret=0 不算过。
14. **C++ 默认参数 + 重载 → Java 移植陷阱**：`convert(X*, bool=false)` 的单参调用在 Java 落到父类单参方法（自己）→ switch 分派无限自递归。**修法**：显式补默认参。鉴别特征：StackOverflow 且堆栈同一行号重复。
15. **同一函数名多命名空间版本（XLS::RgceLoc vs XLSB::RgceLoc、CSVWriter getColAddress vs MulBlank getColRowRef）**——生成器/移植容易 import 错版本；对照 C++ 原文注释区的命名空间限定逐个核对。
16. **C++ NUL 终止缓冲 vs Java String**：C++ 越界读 0（条件自然失败），Java charAt 抛异常（CHECK_HHHH 教训）——字符串扫描函数移植必须补边界守卫。
17. **C++ 引用修改函数 → Java 调用丢弃返回值**：`CorrectXmlString(strT)` 类转义/变换函数 C++ 按引用改入参，Java 移植后返回值必须接收（`strT = CorrectXmlString(strT)`）——丢弃即静默失效（fld 占位符 `<#>` 未转义致 XML 解析炸、内容整块丢）。**grep 所有"调用后仍用原变量"的变换函数调用**。
18. **内嵌图片格式病数据**：BMP 的 bfOffBits 可能被当年生成器写错（=2）——C++ GDI+ 宽容、Java ImageIO 严格。修法：catch 后按 14+biSize+调色板 重算偏移写临时文件重试（CBgraFrame.tryReadBmpWithFixedOffset 先例）。
19. **会话状态双轨清理不同步（errorCode=-100 家族）**：ws 断开瞬间 afterConnectionClosed 会 `deleteParticipant`（participants 立删），而 editorDataMap 要等 RemoveDocDataDelayTask（20s 且可被取消）才清——**凡用 participant 存在性判断"用户是否还在"的逻辑都会误杀 sdkjs 断线重连**（重连默认 delay=15s，auth 带旧 sessionId 走 restore）。鉴别特征：日志 `isParticipantActiveLocal() [...] 不存在` + `setOfficeEditorData() 用户不存在或已被移除` + 前端 errorCode=-100 弹窗；重连与首连的区分证据 = 新 handshake 时间 − sessionId 内嵌 timestamp ≈ 15s。相关事实：首开无缓存文档时 auth 的 openCmd 分支在 openDocSyncLock 内**同步**转换（ppt 实测约 8s，正常不慢；但若转换线程死亡则锁泄漏，见坑 21）；锁等待 5 次×10s=50s 超时；sdkjs 重连 attempts:50 兜底。
20. **日志时间线分析技巧（本次 -100 定位实战）**：①秒级时间戳不够时用 sessionId 内嵌 timestamp（dockey-<ts>-wsId）精确对齐；②clearOfficeEditCache 的 delDir 列表可反推转换现场结构（data/<t1>/<t2>/pptx_unpacked=NExtractTools 自动临时目录，m_sTempDir=null 时建于 bin 旁）；③jstack 现场验证"线程卡死"假设（本次证明转换线程已死但锁还在=毒 class 铁证）；④`convertOfficeFileToBin formatFrom:...` 日志是转换起点的权威标记，缺失=转换未被调用；⑤**Java 版 ppt→bin 是两段**：`ppt2pptx_dir`（先解成 pptx 目录，这就是 pptx_unpacked 的来源）→ pptx→bin——不要以为是 pptx 假扩展名。
21. **ECJ 毒 class（最阴险的一类事故）**：Eclipse 编译器遇到语法错误**照样生成 class 文件**，内容是运行时抛 `java.lang.Error: Unresolved compilation problems` 的桩——不启动报错、不部署报错，**直到撞上那行代码才炸**，且 Error 穿透 `catch (Exception)` → 线程静默死亡 + 锁泄漏 + 无任何错误日志（前端表现为永远"加载中"）。**纪律**：①javac 全批改动文件必须一次编过再提交（提交前 `javac -d /tmp/check` 干跑验证语法）；②插桩清理后必查 try/catch 配对完整性（本次 5e598ba9 事故=清理脚本删了 catch 体留下裸 try，且 DiagTiming 验证时跑的是旧 class 未暴露）；③"加载中+只收心跳 h+无错误日志+等锁 state:1 详情显示旧时间"是毒 class/锁泄漏的组合指纹——jstack 找不到持锁线程即实锤。
22. **基准仲裁要用 C++ x2t 产物而非"正确显示"的 pptx**：PowerPoint 另存的 pptx 与 x2t 系对同一 PPT binary 的表达可不同但视觉等价（本例 bg2 vs lt2 经 clrMap 指向同一 theme 槽）；差异判定标准=C++ 产物（同源转换器语义）。**对比方法**：把 Java 产物与 C++ x2t 产物分别解包，逐形状比对 fill（solidFill 的 schemeClr/srgbClr/alpha、noFill）、master 的 p:bg、media 文件像素（python 解 BMP/PNG 像素对比）。
23. **`(BYTE)` 截断家族再+3（alpha 三连）**：`Alpha = (byte)Math.min(255, x)` 直接赋 long——255→-1。**已修 4 处**：lineOpacity（前人）、fillOpacity/fillBackOpacity/shadowOpacity（本次）。**grep 纪律**：`Alpha.*= (byte)` 一律 `((byte)...) & 0xFF`。
24. **vector& 引用参数输出陷阱（CorrectColorScheme 实锤）**：C++ `void f(vector& v) { v = other; }` 拷贝到调用方；Java `void f(Vector v) { v = other; }` 只重绑定局部引用——**输出参数语义必须原地 clear+add**。grep 纪律：Java 方法内 `参数名 = 局部容器` 的模式全查一遍。
25. **ImageIO 两大静默坑**：①**读**坏头 BMP 抛 IIOException 可 catch 兜底（已有 tryReadBmpWithFixedOffset），但**返回 null 不抛**时不进 catch——img==null 也要走兜底分支；②**写**带 alpha 的 BMP 直接返回 false 不抛（TYPE_4BYTE_ABGR→"bmp" 不支持）——ImageIO.write 返回值必须检查并兜底（丢 alpha 合成 RGB 重写）。另：CBgraFrame 的像素级修改只落 m_pData，SaveFile 写缓存 image——**改完 m_pData 必须置空 image** 强制重建。
26. **std::map 有序性依赖（TreeMap 事故）**：C++ `std::map` 迭代=按 key 升序，Java 移植随手用 HashMap 则迭代序随机——**凡后续逻辑依赖遍历顺序（坐标表/有序收集/去重排序）的一律 TreeMap**。本例：ProtoTable 列/行坐标表无序 → 表格合并推导倒挂泛滥+列宽乱序。grep 纪律：`new HashMap` 出现在"构建坐标/索引/有序集合"语境时逐个核对 C++ 原版容器类型。
27. **生成器 init 区被注释的初始化=裸字段 null 富矿**：`//this.m_exHyperlinkAtom = new ...` 这类被注释行就是 C++ 值成员的对应物——**遇到 NPE 先查该类 init() 有没有成片被注释的初始化行**，恢复即可（本日五连：ExHyperlink/MouseInteractive/InteractiveInfo 四 String/ExtraClrScheme.clrScheme）。另：**CommonBase.reserve 的"垫 null"实现是 C++ reserve 语义错误模拟**（reserve 只留容量不动 size）——凡见到 `= CommonBase.reserve(arr, n)` 后按索引 get 的模式要警惕 null 元素。
28. **USHORT 家族再+1（GID）**：PDF 字体子集的 GID 是 unsigned short——凡 `Map<Short,...>`/`(short)gid` 的模式，GID>32767 必变负。修法：Integer key + 去 (short)。另：**SaveToStream 类的 catch 静默吞异常是"假失败/半成品文件"的温床**——写文件链路的 catch 一律打日志（本例 33KB 无 %%EOF 的截断 PDF+错误码，静默 catch 让日志看起来"几乎成功"）。
29. **页眉页脚 framePr 固定高度陷阱**：老文档页脚页码常用 `<w:framePr w:h="32768">`（固定高浮动框）——**Word 视为自动高度**（另存规范化 h=0），**sdkjs 忠实执行**导致正文区被挤压（表格重排混乱）。转换链已规范化（WriteHdrFtrItem）。鉴别路径：表格混乱但正文/样式/设置全部等价时，**查 header/footer 的 framePr**。另：**部件级二分法**（正常 docx 底座逐部件换入嫌疑部件）是"内容等价但显示不同"类问题的定位利器（V10-V24 共 15 轮 2 小时定位到单属性）。
30. **changes 目录不是纯 changes 目录**：apply_changes 成功后会把 media 图片拷回 changes/ 打进 changes.zip（版本历史机制，C++ 同款）→ **下一轮保存原地复用该目录时图片还在**，而 getDoctXml（C++ 原版同款）无过滤列全部文件给 CChangesWorker 当 change 流解析（PNG 二进制被当 `<len>;<base64>"` 流解码）。鉴别特征：保存链 AIOOBE 的**索引值=changes 目录里某个图片的文件大小**。已修（只列 .json）。另记住：`<Change>` 列表唯一消费者是 CChangesWorker，图片本体 sdkjs 从 ImagesDirectory（bin 旁 media/）取。**影响面是全家族**：getDoctXml 被 apply_changes（保存）、doct_bin2pdf（打印/预览）、doct_bin2epub/fb2/html（导出）共用——修一处全治好（先例：issue IKWODZ 的打印/预览失败随保存卡修复同日消失，真·修复前基线 doct_bin2pdf:3093 同款 AIOOBE 实证）。**对照实验基线纪律**：用户提交后 HEAD 前移，"修复前基线"必须取 `<fixcommit>^`，且 `-verbose:class` 验证 scratch class 真被加载。
31. **装箱 Boolean 裸 if 拆箱 NPE 家族**：C++ nullable 的 `m_pPointer` 是**指针**，`if (m_pPointer)`=判空；Java 移植成装箱类型后同样写法=**自动拆箱**，null 时 NPE。先例：nullable_bool.ToAttribute（documentProtection 序列化炸保存链）。grep 纪律：`if (m_pPointer)`/`if (xxx.m_pPointer)` 的装箱类型（Boolean/Integer/Long）一律 `!= null` 显式判空（同族：坑 16 NUL 终止、坑 11 `>>>`——都是"C++ 隐式行为直译成 Java 崩溃"）。
32. **GraalJS `js.nashorn-compat` 的 ES5 陷阱（2026-11-20 Excel 打印卡实锤）**：nashorn-compat=true 会**默认把 ecmascript-version 压到 5**——ES5 无原生 Promise → sdkjs 的 Closure polyfill 注册器（`nh("Promise",...)`，factory 首行 `if(Ha)return Ha`）装入自制 Promise 垫片 → 垫片调度器 `var de=kh.setTimeout` 在**模块加载时按值捕获**了 native.js 的空桩 setTimeout → **所有 Promise 异步链永不执行**（症状：cell 编辑器 zc 渲染器 null → xlsx 转 PDF 全炸 `null.Lbi`；更隐蔽的：保存链**静默丢内容**——definedNames/筛选状态/activeTab）。修复=对齐 C++ V8（完整 ES6+）：Engine 显式 `.option("js.ecmascript-version","latest")`。**排查教训**：①"引擎不排干微任务"的初步结论要用**独立最小 Context 探针**验证（默认选项下排干正常——真实环境测到的 mt=0 是垫片行为，不是引擎行为）；②尾部注入"同步化 setTimeout 适配器"无效——`de` 按值捕获早于注入；③凡 sdkjs 在服务端有"异步/deferred/Promise"行为异常，先查 `String(Promise)` 是不是 `function Da`（垫片标志）。另：Nashorn 模式（ES5.1）下该缺陷依旧，属已知边界。
